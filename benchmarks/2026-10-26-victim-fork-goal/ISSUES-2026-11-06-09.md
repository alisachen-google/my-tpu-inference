# KV offload to decode DRAM (PR 1992 / hybrid PR 1991): issues found and fixed, 2026-11-06 to 11-09

Scope: code review plus live validation of the "decode DRAM as a KV offload extension of the prefill DRAM offload"
PRs on 1P1D, 1P2D, 2P1D (2P2D pending a fourth host), with write-back on both arms and sticky routes as the
headline cases. Heads at the time of writing: PR 1992 `dc585b07a9` (ready for review), hybrid PR 1991 `6b3c3bb0ba`
(draft, one open defect). The run log is `results/goal_followup_log_2026-11-06_09.txt`; the stage scripts are in
`harness/goal/`.

## 1. Code defects found and fixed (all with regression tests)

Two independent review passes aimed at hangs, silent failures and leaks, plus what the live runs exposed.

No silent acceptance; every engine exited within seconds with its port free. Refused by the PR, naming the setting: HiCache
off, non-raiden HiCache I/O backend, decode `--sleep-on-idle`, Raiden pipeline transfer on the decode, hybrid model (earlier).

## 1b. Open gap found by the shared-prefix stage (2026-11-09 09:21): no recall under a shared hot prefix

Workload: 16 sessions that share an 8k-token prefix (a system prompt) before their own 131k tokens, one request at a
time, PR 1992 head `5a6f9d1f3d`, g + v7. Result: 32/32 requests, 14 pushes landed on the decode, **0 recalls**; every
return found only the shared 8k tokens in the prefill's cache (client `cached_tokens` = 8192 for all 16 sessions, TTFT
p50 7.9 s, a full recompute of the 139k-token prompt). Cause, from the code: an offer is the deepest matched node whose
*whole path from the root* has its full KV in host RAM (`deepest_host_backed_path`), and the prefill's own `have` prefix
is likewise host-backed only (`host_backed_prefix`). The shared chunk is hot, so on both engines it lives on the device and
never gets a host copy under write-back; the pushed per-session tails below it are therefore never offered. The design
assumes host-contiguous paths from the root, which holds for independent sessions (every result in the PR) and fails for
the most common production shape, a shared system prompt. Fix direction: offers that start at a page offset below a
device-resident prefix the prefill already holds (offer carries `first_page`; the prefill's `have` counts device-matched
pages; the landing inserts the host-only tail below the device node with the adopted-backup rule covering it). This is a
protocol change (both roles must run the same build) and is queued as a follow-up item (A8) rather than folded into the
current head. The full stage (16 sessions one at a time, 20 and 24 at 4 concurrent) ran on both trees: 240/240 requests,
no exception, no out-of-memory, no refused drop, and no recall on either tree.

## 1c. Review comments and simplification (2026-11-09, later)

Claude's seven inline review comments on PR 1992 are resolved on head `072eca7452` (each with a unit test and a reply on the
thread): the installer import (already fixed), the host-pool control port (already fixed), a memory release for a weight
update now lets the offload's transfers settle before the weight updater's idle assertion, `PullReq`/`ReshardReq` omit
default fields on the wire (an older prefill still serves a decode with the switch off) and `ReshardReq` carries the switch
so a decode with it on at another attention TP is refused instead of served without the offload, a host read whose poll
keeps raising is failed after the transfer deadline, and a refused recall is given up before any landing page is reserved.
A simplification pass removed about 60 non-test lines (one path walk, one agreed allocation helper, argument checks no
longer repeated at manager level, dead parameters and an unused helper); `core_hooks.py` was renamed
`dram_offload_hooks.py`. The shared-prefix fix is PR 2052 (draft, stacked on 1992) with issue 2051; its live validation and a
rough live check of the simplified tree run on g + v7 after each other; the rough check passed on head `072eca7452` (integrity 16/16, 16-session recall 58.4 % prefill-side hit against 58.7 % before, mixed sizes 120/120, no exception). First live result of the fix (12:03): with
4 concurrent requests the shared-prefix sessions recall again (20 sessions 64.3 % prefill-side hit, 24 sessions 61.1 %, 265
of 265 pushes stored, 50 pulls, no failure, no out-of-memory; the independent-session point stays at 70.4 %); one request
at a time still pushes nothing, because host pressure arrives with less free host room than the shared chunk needs and the
rank-agreed room check for its backup fails. The fix is being extended to make that room (host eviction and duplicate
reclaim, agreed across ranks) before the backup.

## 2. Open defect: hybrid prefill out of memory (PR 1991)

On 2026-11-07 19:14 the gpt-oss prefill died with `Prefill out of memory` during the single-request output-equivalence
run (one 128k+8k request at a time, the fifth recall). The device had 646k evictable tokens, but the host pool was full,
so the write-back backup of each evicted leaf failed and core's `drop_subtree_no_host` fallback was refused for every
candidate because of a lock or pending DMA in the subtree; core raises instead of waiting. The same run passes on the
full-attention PR. A fresh single-request run on another pair (g + v7) passed, 16/16 exact; the full sequence
(sweep -> edges -> integrity) is being re-run with a diagnostic build that logs the exact lock state of every refused
drop. The first diagnostic attempt showed that refusals do happen during the recall workload (admission of a recalled
prefix evicts other leaves), but my hook itself crashed the engine (it iterated `component_data.items()`; the tree keeps a
list) and was fixed and CPU-tested before the rerun. A third run (fresh engines on g + v7, 2026-11-09 03:16-03:52) passed every case: edges E1-E5, single-request
integrity 16/16 exact with 13 recalls, mixed sizes 120/120, and 96 refused-drop dumps without an OOM. The dumps show the
refused subtrees are device-resident, unbacked chunk nodes whose host-only descendants (the 128-token window nodes of a
recalled prefix) carry a host lock on the full-attention component only. CPU probes of the pin and path-lock helpers show
both lock and release cleanly, so the open question is whether those locks are in-flight recall state or a slow leak that
needs an engine instance with history (the Nov 7 instance had served the sweep and the edge cases first). An accumulation
run on one instance (sweep, edges, integrity, mixed) with a lock-state line every 60 s is in progress.

Resolution (2026-11-09 04:50): the lock-state timeline shows the host locks are core HiCache's per-request locks (a host lock
walks up through host-only ancestors, so an in-flight load-back locks every window node of the active session) and they
return to zero after every flush, so there is no leak in the extension. The mechanism is a shape the recall insert
created: core's host insert under write-back keeps the received copy of a backed node only, so a device-only node on the
matched path (a shared hot prefix) stayed unbacked above the host-only recalled branch. When the host pool is full its
backup fails and core's fallback drop of the subtree is refused while the request holds the branch's host pages; after the
candidates run out core raises `Prefill out of memory` with evictable tokens still counted. Fix (both PRs, folded into the
recall commit): the received pages of such a node become its backup (`adopt_received_backups`, counted as
`adopted_backup_tokens`), so eviction demotes it like any backed node. Unit tests cover the adoption, the already-backed
case and the caller-owned prefix; the eviction-walk tests build their shape through core directly. The accumulation run itself (sweep, edges, integrity, mixed on
one pre-fix instance, 2026-11-09 03:59-05:03) passed as well, with the host pool full during the integrity run
(1,920 of 943,744 tokens free) and 112 refused drops but no out-of-memory: the Nov 7 failure is timing-dependent and was not
reproduced in four attempts, so the fix rests on the analyzed shape and its unit tests. Live validation on both new heads (2026-11-09 06:05-06:44, g + v7): PR 1992 integrity 16/16 exact with 12 recalls,
16-session recall 32/32, mixed sizes 120/120; hybrid PR integrity 16/16 with 13 recalls, recall 32/32, mixed 120/120; no
engine exception. The adopted-backup counter stayed at 0 in these workloads (their sessions share no hot prefix), so a
shared-prefix recall workload is being added to exercise the fixed shape live.
