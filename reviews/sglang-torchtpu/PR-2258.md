## What it does

A health request is supposed to establish that inference is progressing. On a disaggregated Decode worker, a probe arriving while idle can be preallocated just before user KV arrives. Mixing that probe into a user batch changes the batch shape solely for health checking, potentially changing compilation/bucketing and measurement behavior.

The new policy separates probe and user batches:

| Situation | New behavior |
| --- | --- |
| A probe is still running | Finish its bounded forward before admitting waiting users. |
| Users are running or waiting | Admit users; leave a queued probe out of their batch. |
| Useful inference completed after the probe was admitted | Remove the queued probe and release its request row, owned KV, prefix pin and applicable auxiliary state. |
| Selected users all finish during the fake prebuilt handoff | Run a queued probe alone in a second admission pass, even if more users remain queued. |
| Probe has already finished but remains in the running list | Exclude it from admission capacity so it does not delay waiting users. |

The admission sequence is stored once on `Req` and preserved on requeue. Cleanup compares it with the monitor's useful-completion sequence, not rank-local TTL expiry. Python Decode probes request two output tokens and ignore EOS: the fake prebuilt token cannot finish the probe before a real decode forward. One-token users, aborted users and stop-token users are handled using actual prebuilt finish processing, rather than speculative prediction.

Because scheduler probe recognition still uses the `HEALTH_CHECK` RID prefix, the PR reserves that namespace in Python tokenizer intake and Rust HTTP `/generate` parsing. Python's health handler opts in via a function keyword, not a client JSON field. The reservation is incomplete for another Rust client entry point, as F1 explains.

## F1 — P1 reliability / input boundary: Rust gRPC still admits client probe IDs

**Changed location:** [`request.rs:291–302`](https://github.com/sgl-project/sglang-torchtpu/blob/f3ffa42b5cd11d317f67c355c2d62fe812c97dbf/rust/sglang-server/src/message/request.rs#L291-L302), combined with the new [unfinished-probe admission guard](https://github.com/sgl-project/sglang-torchtpu/blob/f3ffa42b5cd11d317f67c355c2d62fe812c97dbf/python/sglang/srt/disaggregation/decode.py#L3326-L3331).

**Trigger:** on a Rust gRPC frontend serving PD Decode, a client submits a valid long `Generate` or `TextGenerate` request with a RID such as `HEALTH_CHECK_client` while the worker can admit it. The output length is client-controlled; it is not the health handler's two-token request.

**Call path at this exact head:**

1. [`GrpcService::{generate,text_generate}`](https://github.com/sgl-project/sglang-torchtpu/blob/f3ffa42b5cd11d317f67c355c2d62fe812c97dbf/rust/sglang-server/src/grpc/mod.rs#L92-L133) calls its converter and `FrontendHandle.generate` directly. It does not call `GenerateBody::into_requests`, where this PR adds the reservation.
2. [`grpc/convert.rs`](https://github.com/sgl-project/sglang-torchtpu/blob/f3ffa42b5cd11d317f67c355c2d62fe812c97dbf/rust/sglang-server/src/grpc/convert.rs#L149-L179) calls `request_id(rid)`, which unconditionally uses `Rid::from_client` for a supplied ID. The text path does the same at line 86.
3. [`Rid::from_client`](https://github.com/sgl-project/sglang-torchtpu/blob/f3ffa42b5cd11d317f67c355c2d62fe812c97dbf/rust/sglang-server/src/message/ids.rs#L89-L100) appends a uniquifier; it does not remove the `HEALTH_CHECK` prefix. The shared [scheduler-intake validator](https://github.com/sgl-project/sglang-torchtpu/blob/f3ffa42b5cd11d317f67c355c2d62fe812c97dbf/rust/sglang-server/src/tokenizer_manager/to_scheduler_validation.rs#L14-L38) checks RID length, not the reserved prefix. Rust dispatch bypasses Python `TokenizerManager.generate_request` too.
4. The scheduler classifies that request as a probe. While it is unfinished in `running_batch`, the new guard returns before admitting any waiting user. A long client request can therefore monopolize admission for its generation lifetime. If a newer useful completion instead retires it while queued, the probe-specific cleanup is also inappropriate for a client awaiting ordinary generation output.

**Evidence:** source tracing establishes the missing validation boundary. [probe_pr2258_admission.py](../../tests/health_probe_review/probe_pr2258_admission.py) executes the real selector with a prefixed, suffixed client ID and reproduces waiting-user exclusion on three consecutive unfinished steps, followed by admission when the client finishes. The probe does **not** execute Rust, a live gRPC service or a model. The scheduling consequence is new even though accepting prefixed IDs in the converter predates the PR.

**Fix:** apply the namespace check to both untrusted gRPC conversions, ideally through a shared client-RID validation helper used by all external adapters. Preserve the separately trusted internal health constructor. Add RPC/conversion tests asserting `INVALID_ARGUMENT` for both methods and successful ordinary-ID requests.

**Ready-to-paste inline comment:**

> P1 reliability: This reservation only covers Rust HTTP `/generate`. `grpc::convert::{generate,text_generate}` constructs `FrontendRequest` directly, and `request_id` preserves a client's `HEALTH_CHECK` prefix through `Rid::from_client`. Shared intake does not reject it. Such a long request still reaches the new probe guard and prevents waiting users from being admitted until it finishes. Please validate the namespace at both gRPC client boundaries as well, with rejection tests and an internal-probe exception.

## F2 — P1 validation: the CUDA checksum suite rejects the new keyword

**Changed location:** [`decode.py:3248–3250`](https://github.com/sgl-project/sglang-torchtpu/blob/f3ffa42b5cd11d317f67c355c2d62fe812c97dbf/python/sglang/srt/disaggregation/decode.py#L3248-L3250).

`get_new_prebuilt_batch` now always forwards `health_check_only`, including its default `False`. The existing [`TestGetNewPrebuiltBatchChecksum._run_once`](https://github.com/sgl-project/sglang-torchtpu/blob/f3ffa42b5cd11d317f67c355c2d62fe812c97dbf/test/registered/unit/disaggregation/test_kv_checksum.py#L263-L278) patches the callee with `lambda s, rb: batch`. That lambda accepts no keyword, so all seven tests in that class fail before the checksum path is reached when CUDA is available.

**Evidence:** the local probe extracts the actual wrapper and the exact lambda from the reviewed test file; invoking them reproduces `<lambda>() got an unexpected keyword argument 'health_check_only'`. The base wrapper calls the helper with only `running_batch`. This is an interface regression in the test fixture, not a production checksum failure. The suite registers in CUDA `base-b-kernel-unit` with `1-gpu-large`; its `setUp` skips without CUDA, so passing CPU checks do not exercise it.

**Fix:** update the patched helper to accept the keyword, or forward it only when the new mode is requested if retaining compatibility is intended. Run the seven CUDA checksum integration cases afterward.

## Verified non-issues and manual validation

- Cleanup calls the existing cache-finish and `release_kv_cache(..., is_insert=False)` paths, preserving the distinction between shared prefix pages and the request-owned tail. Host receive and HiSparse cleanup mirror the corresponding failure lifecycle. Full allocator behavior was read, not rerun locally.
- A useful completion advances the sequence even without pending HTTP probes. Local TTL expiry controls notification bookkeeping but no longer determines this selector's cleanup. Requeue preserves the original admission sequence.
- The second pass runs only after the first leaves no running requests. It does not mix an active user batch with probes or admit a second user cohort in the same pass.
- These are shared PD scheduler/frontend changes, so keeping them in core is appropriate. They introduce no TPU import, `is_tpu()` branch, or backend-specific default. Review/qualification must include CUDA and other affected PD backends, not only TPU.
- Python multi-tokenizer workers inherit the updated `TokenizerManager.generate_request`; its new keyword defaults to false for existing callers.
- The Rust native health frontend still uses a one-token/global-response-activity scheme at [`frontend.rs:268–309`](https://github.com/sgl-project/sglang-torchtpu/blob/f3ffa42b5cd11d317f67c355c2d62fe812c97dbf/rust/sglang-server/src/frontend.rs#L268-L309). That is pre-existing and unchanged here; do not describe this PR as bringing all native health semantics into parity with Python's useful-inference acknowledgement. It is a follow-up boundary, not an additional introduced defect.

The remaining broad validation need is a real multi-rank PD run with overlap enabled/disabled, a full request pool, host-receive state, and one-token backlogs. Check batch membership, completion agreement, queue drainage and pool baselines. No new device op is added, but CPU stand-ins cannot establish collective ordering or asynchronous lifetime correctness on hardware.
