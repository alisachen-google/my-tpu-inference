## What it does
Builds the storage/lifecycle layer for Qwen3.8-Flash's PLE n-gram table on top of the common PLE layer from #1974 (`models/vllm/qwen4_exp/ple.py`) and the Pallas lookup/conv kernels from #1966 (`kernels/qwen4_exp/ple.py`, `pool.py`). The common layer gains an injectable `table_factory`, an optional explicit `parallel_group`, a `compute_ids` split and a `gated_values` split; defaults are unchanged. `ple_storage.py` adds `ResidentPLETable` (CPU staging via the upstream shard loader, one compact int16/uint8 table on device, CPU copy freed) and `HostPLETable` (bytes stay on CPU, optionally in a sealed memfd shared by the DP engines of one TP rank via `ple_host.SharedPLETable`, a flock/JSON-controlled writer election with `/proc/<pid>/fd` attach). `parallel.py` + `pooled_ple.py` provide the TP-or-TP*DP ownership transport of encoded rows (integer all_reduce of the carrier bits) and the `Qwen4ExpPooledPLE` adapter that composes common hash/projection/gate math with the native request-history conv kernels; `ple_offload.host_lookup` is the custom-op boundary for the host gather. Model/runner wiring (who constructs the adapter, registers it in the forward context, calls `finalize_weights`, sets `model_config._qwen4_exp_ple_host_launch`) is deferred to #1968, so several entry points here are not yet reachable.

## Recommendation
REQUEST CHANGES — the shared-host lifecycle has a verified operational defect (a crashed or timed-out generation permanently poisons its key with no recovery path or diagnostic), and the DP-wide ownership transport relies on an unstated lockstep-bucket assumption that this backend's DP mode does not provide; both need an answer before the storage API is frozen for #1968.

## Findings

### F1. A failed shared-table generation is permanent; nothing can reclaim it  [major]  `src/vllm_torchtpu/models/vllm/qwen4_exp/ple_host.py:91-95`, `:149-151`, `:261-268`
`SharedPLETable.__init__` (reader branch, line 91-95) calls `_check_error` / `_check_writer` unconditionally. Any generation that ends with `status == "error"` (abort on any `finish()` exception, `close()` before ready, a participant death) or with a dead writer in `status == "loading"` is rejected forever: there is no check that the recorded writer and all members are dead, no TTL, and the control file is never unlinked on the failure path (by design, "retained on error"). I verified with a stdlib-only probe against the head: writer process killed before publication -> reader's `finish()` raises `PLE shared writer exited before publication`; after every process has exited, two fresh `SharedPLETable(...)` launches with the same key both raise the same error and the 282-byte JSON stays in the directory. The error text does not name the control file, so an operator cannot tell what to delete. Whether this bites in production depends entirely on `launch["instance"]` being unique per launch (`shared_ple_options`, line 23-31), and nothing in this PR or the worktree sets `model_config._qwen4_exp_ple_host_launch`, so the invariant is unverifiable here. If `instance` is derived from anything stable (model name, port, host), one crash blocks every later launch of that model on that host until someone finds `/tmp/vllm-qwen-ple-<uid>/<sha256>.json`.
**Suggested comment:**
> `SharedPLETable` rejects a key forever once a generation has failed (`status == "error"`, or `loading` with a dead writer): `__init__` raises from `_check_error`/`_check_writer` even when every recorded pid is gone, and the failure path never unlinks the control file. I reproduced it: kill the writer before `finish()`, let every process exit, and any later `SharedPLETable(...)` with the same key raises "writer exited before publication" indefinitely. Two asks: (1) when the recorded writer *and* every member are dead (`_process_identity` is None for all of them), treat the record as reclaimable, i.e. truncate the file under the lock and become the new writer, instead of raising; (2) include `self._path` in the error text so an operator can recover by hand in the meantime. Also, what guarantees `launch["instance"]` is unique per launch? It is read from `model_config._qwen4_exp_ple_host_launch`, which nothing in this PR sets; if it is derived from something stable (model path/port), the retained marker turns one crash into a permanent outage for that key.

### F2. TP*DP ownership assumes every DP rank runs the same padded bucket in lockstep  [major, question]  `src/vllm_torchtpu/models/vllm/qwen4_exp/parallel.py:15`, `:25-28`, `:44-46`; `src/vllm_torchtpu/models/vllm/qwen4_exp/pooled_ple.py:121`, `:129-136`
`gather_ids` does `dp_group.all_gather(ids, dim=0)` and `combine` narrows at `dp_group.rank_in_group * local_tokens`, so both the all_gather and the row selection are only correct if every DP rank calls them at the same step with the identical `local_tokens` (the comment at line 43 says "physical buckets", which presumes a shared bucket). In this backend, non-EP DP runs as independent per-engine `tpu_dist` worlds (`worker/tpu_worker.py:204-215` collapses `data_parallel_size` to 1), so `get_dp_group().world_size == 1` and `embedding_across_dp=True` silently degrades to TP-only ownership (line 15) with no warning; the user asked for the memory split and gets the TP-replicated table instead. With EP (the only mode where DP ranks share a world), vLLM coordinates `num_tokens_across_dp` per step but each rank keeps its own padded bucket; rank A at bucket 8 and rank B at bucket 16 makes `all_gather_into_tensor` fail (or, if the communicator pads, `narrow` at `rank*8` reads rank A's rows for rank B). The multichip tests only ever use one `slots` value for all eight ranks, so this is not exercised. `host_lookup` has the same contract (`dp_size * local_tokens` rows at line 129-136).
**Suggested comment:**
> `PLEParallel.gather_ids`/`combine` and `host_lookup` are only correct if all DP ranks execute the same padded bucket at the same step. Where is that guaranteed? In vllm-torchtpu non-EP DP engines are independent worlds (so `dp_group.world_size == 1` and `embedding_across_dp` silently becomes TP-only ownership: please raise or at least log when the request cannot be honoured), and with EP the ranks only agree on `num_tokens_across_dp`, not on a common bucket. If #1968 pads every DP rank to the DP-wide max bucket, please state that in the class docstring and add an assertion in `combine` (e.g. compare `result.shape[0]` against `dp_size * local_tokens`); the multichip tests should include at least one scenario where ranks run different `slots` to show the failure mode is caught rather than silent.

### F3. Shared control directory is trusted without ownership/symlink checks and must be identical for all participants  [minor]  `src/vllm_torchtpu/models/vllm/qwen4_exp/ple_host.py:27`, `:64-70`, `:97-100`
`directory.mkdir(mode=0o700, exist_ok=True)` accepts a pre-existing directory of any owner/mode and follows a symlink; `O_NOFOLLOW` on the file does not help if the directory itself is the attacker's (probe: a symlinked, group-writable directory is accepted silently). A hostile same-host user who pre-creates `/tmp/vllm-qwen-ple-<uid>` can plant a `<sha>.json` whose `writer.pid/fd` points at any same-uid process's fd; the reader only checks inode and size. Separately, the directory comes from `tempfile.gettempdir()` per process, and attach goes through `/proc/<pid>/fd/<n>`, so DP engines with different `TMPDIR`, a different PID namespace (one container per DP rank) or `hidepid` on `/proc` will each elect themselves writer and all time out after 600 s with "participants did not become ready", which does not say why.
**Suggested comment:**
> Please `os.lstat` the control directory after `mkdir` and reject it unless it is a real directory owned by `os.getuid()` with mode 0700 (classic `/tmp` pre-creation attack; the `O_NOFOLLOW` on the JSON does not protect the directory). Also consider making the directory explicit (an env/config knob with the `gettempdir()` value as default) and documenting that all participants need the same `TMPDIR`, the same PID namespace and readable `/proc/<pid>/fd` — today a mismatch surfaces only as a 600 s timeout.

### F4. Unreachable helpers and a private attribute on vLLM's ModelConfig  [minor]  `src/vllm_torchtpu/models/vllm/qwen4_exp/ple_host.py:16-31`
`host_available_memory()` and `shared_ple_options()` have no caller in the worktree, and the latter reads `model_config._qwen4_exp_ple_host_launch`, which nothing sets. Both are dead in this PR and the second couples the storage layer to an undocumented, underscore-prefixed attribute that must be monkey-set on vLLM's `ModelConfig` by #1968.
**Suggested comment:**
> `host_available_memory` and `shared_ple_options` are not called anywhere in this PR, and `shared_ple_options` depends on a private attribute (`model_config._qwen4_exp_ple_host_launch`) that is not defined here. Either move them to #1968 with the code that sets the launch descriptor, or define the descriptor (a small dataclass with `instance`/`participants`) in this PR so the key/identity contract — including whether a checkpoint fingerprint is part of `identity` — can be reviewed with the storage.

### F5. The reader side of `HostPLETable` is never exercised on CPU  [minor]  `tests/models/vllm/test_qwen4_exp.py:1109`, `:1227`; `src/vllm_torchtpu/models/vllm/qwen4_exp/ple_storage.py:209-241`, `:268-273`
Both CPU tests that use `shared=` pass `participants=1`, so the process is always the writer. The non-writer path — meta `weight`, `_copy_checkpoint` skipping the copy, `finalize_weights` running `process_weights_after_loading` against a meta tensor, the `finish()` barrier from the reader side, and `lookup_host` reading through `SharedPLETable.buffer()` — only runs in the eight-rank TPU test. `test_qwen4_exp_ple_host.py` covers `SharedPLETable` readers, but not through `HostPLETable`.
**Suggested comment:**
> Could you add a spawn-based CPU test that builds two `HostPLETable`s with `participants=2` (one process is the reader) and checks `lookup_host` on the reader after `finalize_weights`? Today the meta-weight reader path (`allocate_embedding_weight` -> meta, `_copy_checkpoint` no-op, `process_weights_after_loading` on a meta weight, `lookup_host` via `buffer()`) is only covered by the multichip TPU test.

### F6. Table construction has a cross-process side effect and no finalizer; timeout is not configurable  [minor]  `src/vllm_torchtpu/models/vllm/qwen4_exp/ple_storage.py:210-222`; `src/vllm_torchtpu/models/vllm/qwen4_exp/ple_host.py:52`
`HostPLETable.__init__` (via `allocate_embedding_weight`) registers the process as a participant and may elect it writer, before any weight has been loaded. If model construction fails later in the same process (any other layer raising), nothing calls `close()`, so peers see a live writer that never publishes and wait the full 600 s. The 600 s default is hard-coded in `SharedPLETable.__init__` and not plumbed through `SharedPLEOptions`; DP engines whose `load_model` phases are staggered by more than that (cold checkpoint cache, sequential pod start) will abort and, per F1, poison the key.
**Suggested comment:**
> Two robustness asks: (1) register a `weakref.finalize(self, table.close)` (or an `atexit` hook) when `SharedPLETable` is created in `allocate_embedding_weight`, so a construction failure elsewhere in the process releases the writer slot instead of stalling peers for `timeout`; (2) expose `timeout` on `SharedPLEOptions` — `finish()` is a cross-engine barrier at the end of weight loading and 600 s is easy to exceed when DP engines start at different times.

## Test coverage assessment
The CPU suite (`test_qwen4_exp.py` additions) covers factory injection, explicit-group sharding, the resident/host/shared loaders through the upstream shard loader (bf16 and fp8), duplicate/missing-row validation, and bit-exact adapter parity against the common layer with the device kernels replaced by dense doubles; `test_qwen4_exp_ple_host.py` is stdlib-only and genuinely spawns processes to prove early-attach-then-seal (the "one writer, sealed mapping" claim holds: readers map read-only before the writer seals and cannot read until `status == "ready"`), writer death, identity mismatch, metadata mismatch and bounded waits — I re-ran equivalent scenarios with the system interpreter and they behave as described. What is not proven: the non-writer `HostPLETable` path on CPU (F5), recovery after a failed generation (F1 — the tests assert the opposite, that the marker is retained), DP ranks with unequal buckets (F2), symlink/ownership of the control directory (F3), and the compiled `host_lookup` custom op inside a graph (the TPU parity test calls `lookup_for_model` eagerly and compiles only `forward_with_history`). The eight-rank TPU results are self-reported for an earlier tree (`18f76f04a`) and cannot be checked here.
