## What it does
This is the integration PR of the Qwen3.8-Flash stack: it turns the components reviewed in #1960/#1962/#1964/#1965/#1967/#2005 into a running model. Core gets two optional seams: a `ModelAdapter` protocol (`runner/model_adapters.py`) that the runner selects once in `load_model` and consults in `execute_model` (`begin_step` -> one H2D token snapshot, `prepare_inputs` -> explicit model kwargs), in `_dummy_run` (profile/warmup/idle-DP forwards) and in `KVCacheManager.get_kv_cache_spec/initialize_kv_cache`; and a `requires_dp_collectives()` predicate that generalises the existing "EP needs one DP*TP tpu_dist world + lockstep forwards" rule to Qwen's `embedding_across_dp` PLE. On the Qwen side it defines the cache geometry (QSA main KV / BF16 compressed keys / ring+tags, GDN conv+SSM, PLE conv history) as vLLM `KVCacheSpec`s, binds them either as independent typed owners (`cache.py`, env-override path) or into the unified attention-shaped pool (`pool_layout.py` + `pooled_cache.py`, the default for this architecture), forces the scheduler capacity to `1 + max_num_seqs * blocks_per_request`, and activates the `Qwen4ExpForCausalLM` module with per-layer HC, QSA, GDN (with the #2005 chunked-input opt-in) and PLE (resident or host-offloaded with the F.pad overflow-shape fix). The platform now preserves `splitting_ops` declared by model config hooks (needed for the eager `qwen4_exp::host_lookup` boundary).

## Recommendation
REQUEST CHANGES - the core seams are safe for existing models (every new branch is behind `model_adapter is None` / `enable_expert_parallel`-equivalent checks and I found no changed default), but the Qwen integration has a per-step full-batch token upload in the hot path (F1), an HBM precheck that counts one of N pool tensors (F3), and a pool layout that reserves as many bytes for compressed keys as for the main KV while using 1/8 of them (F2) - the last one is a design discussion, the first two should be fixed before this lands.

## Findings (ordered by severity: blocker > major > minor)

### F1. `begin_step` uploads the whole `[max_num_reqs, max_model_len]` token table every step  [major]  `src/vllm_torchtpu/models/vllm/qwen4_exp/inputs.py:85`
`Qwen4ExpAdapter.begin_step` does `batch.token_ids_cpu_tensor.to(device, non_blocking=True)` once per `execute_model` (called from `tpu_runner.py:3750`). `InputBatch.token_ids_cpu_tensor` is `[max_num_reqs, max_model_len]` int32, so this is 4 MiB per step at 128 x 8192, 16 MiB at 128 x 32768 and 128 MiB at the model's 262144 position capacity - on every decode step, to feed `ngram_context_from_store` (inputs.py:108), which then reads exactly `ngram_size - 1 = 2` columns per row. The same information is available on the host (`input_batch.token_ids_cpu`, `num_computed_tokens_cpu`) and the runner already stages per-step host tensors; a `[rows, ngram-1]` int64 gather on CPU is ~1 KB. Two secondary concerns with the current form: (a) `non_blocking=True` from pageable memory, while `_modify_prev_results` (tpu_runner.py:2598-2678, run from `sample_tokens` at 4879) writes into the same CPU tensor during the step - whether torch_tpu stages pageable copies synchronously is not stated anywhere, so the "immutable snapshot" docstring is an assumption; (b) `prepare_inputs` is called per chunk (3962) but the upload is per step, so the cost is paid even for chunks that only need a slice. The GSM8K run (short prompts, APC off) would not show this.
**Suggested comment:**
> `begin_step` copies the full `token_ids_cpu_tensor` (`[max_num_reqs, max_model_len]` int32: 16 MiB per step at 128 x 32k, 128 MiB at 262k) to the device every `execute_model`, only so that `ngram_context_from_store` can read `ngram_size-1` columns per row. Could the n-gram context be gathered on the host instead (the runner already has `token_ids_cpu` and `num_computed_tokens_cpu` for the chunk's rows) and uploaded as a `[rows, ngram-1]` tensor alongside the other staged inputs? That also removes the dependency on `non_blocking=True` from pageable memory while `_modify_prev_results` writes into the same CPU tensor later in the step.

### F2. The pooled `compressed_k` owner reserves as much HBM as the main KV while holding 1/8 (FP8) or 1/16 (BF16) of the bytes  [major, design]  `src/vllm_torchtpu/models/vllm/qwen4_exp/pool_layout.py:137-146`
`pooled_cache_specs` gives the compressed-key spec the same `block_size` and `page_size_padded=page_bytes` as the main KV, so the scheduler allocates `ceil(L/block_size)` full pages per attention layer for it. Per page the compressed owner stores `block_size/ratio * compressed_width * 2` bytes = `block_size * 128` (ratio 4, width 256) versus `page_bytes = block_size * token_bytes` with `token_bytes = 1024` (FP8, TP1) or `2048` (BF16): 12.5 % / 6.25 % used. With the production geometry (FP8 KV, checkpoint-default FP32 SSM, TP1) `derive_pooled_gdn_state_layout` gives `ssm_tokens=3072 + conv_tokens=128 -> block_size=3200`, `page_bytes=3.125 MiB`; a request at `max_model_len=8192` owns `3 pages x 12 layers = 36` main pages (112.5 MiB) and the same 36 compressed pages (112.5 MiB, of which ~14 MiB is data), plus 12 ring pages (37.5 MiB for <= 8 KiB each), 36 GDN and 1 PLE page: ~378 MiB per request, of which ~135 MiB is compressed/ring padding (36 %). The docstring explains why the logical span was not widened (APC alignment), but there is a third option that keeps alignment: put the compressed rows in the tail of the main page (`token_bytes += compressed_width*2/ratio`, i.e. 1152 B/token) so there is no separate owner at all, as the DSv4 path does with `tokens_per_state` inside one spec. Not a correctness issue; it directly caps `max_num_seqs` under the fixed-capacity admission in `config.py:162-167`.
**Suggested comment:**
> In the pooled layout the `compressed_k` owner takes `ceil(L/block_size)` full pool pages per layer (same as main KV) but only fills `block_size/ratio * 256 * 2` bytes of each: 12.5 % with FP8 KV, 6.25 % with BF16. At FP8/FP32-SSM/TP1 (block 3200, 3.125 MiB pages) that is ~112 MiB of compressed pages per 8k request for ~14 MiB of keys, plus 12 ring pages of 3.125 MiB for <= 8 KiB each - about a third of the per-request footprint. Since the scheduler block size has to stay uniform for APC, would it be possible to fold the compressed rows into the tail of the main page (`token_bytes` 1024 -> 1152 and one owner), the way DSv4 keeps compressed state inside one spec via `tokens_per_state`? If that is out of scope here, could the PR description state the per-request HBM cost so the `max_num_seqs` admission failure is understandable?

### F3. The pooled HBM precheck looks at one KVCacheTensor instead of all of them, and nothing verifies the headroom after allocation  [major]  `src/vllm_torchtpu/models/vllm/qwen4_exp/pooled_cache.py:74`
`required = max(t.size for t in config.kv_cache_tensors)` is compared against `budget.available - TEMP_HEADROOM`, but vLLM's `get_kv_cache_config_from_groups` emits one `KVCacheTensor` per layer slot (the non-pooled sibling test `test_qwen4_exp_cache.py:131-135` already observes 40 tensors for 39 groups), and `materialize_kv_cache_tensors` materialises every one of them (`len(self.materialized.raw_tensors)` is logged as "pools"). So the check undercounts by the number of raw tensors, the error message ("needs N bytes") reports a fraction of the real need, and the 8 GiB `TEMP_HEADROOM` promise in the docstring is not enforced: unlike `Qwen4ExpCache.allocate` (cache.py:139-146) there is no post-allocation `after.available < TEMP_HEADROOM` check in the pooled path. The failure mode is a raw allocator OOM inside `materialize_kv_cache_tensors` during `profile_run` instead of the intended "reduce max_num_seqs or max_model_len" error. Test `test_pool_initialize_builds_mamba_plan_from_materialized_layers` stubs `allocate`, so this line is untested.
**Suggested comment:**
> `required = max(t.size ...)` sizes only the largest `KVCacheTensor`, but the planner emits one tensor per layer slot and `materialize_kv_cache_tensors` allocates all of them (the non-pooled test sees 40 tensors for 39 groups). This should be `sum(...)`, and it would be good to add the same post-allocation `compute_hbm_budget(...).available < TEMP_HEADROOM` check that `Qwen4ExpCache.allocate` has, so an over-committed pool fails with the intended message instead of an allocator OOM inside `profile_run`.

### F4. Fixed capacity bypasses vLLM memory profiling, and the config hook is not re-entrant  [minor, design]  `src/vllm_torchtpu/models/vllm/qwen4_exp/config.py:162-167`, `:364`
`verify_and_update_config` pins `num_gpu_blocks_override = 1 + max_num_seqs * blocks_per_request`, i.e. the pool is always sized for every request at `max_model_len`, regardless of HBM; the actual allocation then happens inside `profile_run` (adapter `dummy_run` -> `cache.allocate()`, inputs.py:143), so `determine_available_memory` reports what is left after the pool and vLLM's `gpu_memory_utilization`/`check_enough_kv_cache_memory` accounting operates on that remainder (>= 8 GiB by construction; `check_enough_kv_cache_memory` needs one max-length request to fit in it, which at BF16 KV and 262k context does not). Users must hand-tune `max_num_seqs x max_model_len` to the chip (F2 makes that tighter) instead of getting capacity from the profile. Separately, `validate_config` requires `c.block_size == 128` (config.py:364) but the same hook leaves `cache_config.block_size = layout.block_size` (1664/3200), so any second `VllmConfig.__post_init__` (e.g. `dataclasses.replace(vllm_config, ...)`, which vLLM uses for draft/MM sub-configs) raises "requires BF16/P128". None of this is wrong for an S1 milestone, but the PR body does not say that the planner's HBM-derived `num_blocks` is intentionally discarded.
**Suggested comment:**
> Two questions on admission: (1) the pool is pinned to `1 + max_num_seqs * blocks_per_request` and allocated inside `profile_run`, so vLLM's HBM profiling no longer sizes the cache - is the intent to keep this S1-only, and if so can the description say so (and the error at `pooled_cache.py:76` mention the per-request page cost)? (2) `validate_config` rejects `block_size != 128` while the hook sets `cache_config.block_size = layout.block_size`; a re-run of `verify_and_update_config` on the same config (any `replace(vllm_config, ...)`) fails. Should the check accept `{128, layout.block_size}` or run before the override only?

### F5. Core: adapter early-returns skip side effects the generic paths provide  [minor]  `src/vllm_torchtpu/runner/tpu_runner.py:5461`, `src/vllm_torchtpu/runner/kv_cache_manager.py:1313`
For existing models nothing changes (both branches are `if self.model_adapter is not None`, default `None` set at tpu_runner.py:739 and kv_cache_manager.py:212). For the adapter path, `KVCacheManager.initialize_kv_cache` returns before `register_kv_caches` (kv_cache_manager.py:1223/1797) - fine while `validate_config` rejects `kv_transfer_config`, but #1971 (Raiden P/D) will have to re-add it in the adapter; and the non-pooled `Qwen4ExpCache.initialize` (cache.py:201-299) does not call `_precompile_substitute_placeholder_token` / `_build_mamba_copy_plan` the way `Qwen4ExpPooledCache.initialize` (pooled_cache.py:145-150) does, so async scheduling on the env-override path compiles the substitution kernel at the first serving step. Also `_dummy_run` uses `getattr(self, "model_adapter", None)` (5461) while `execute_model` (3750, 3963) and `load_model` (5174) use the attribute directly - pick one; `__init__` already sets it.
**Suggested comment:**
> Small consistency points on the core seam: `_dummy_run` reads `getattr(self, "model_adapter", None)` while `execute_model`/`load_model` use `self.model_adapter` directly - since `__init__` sets it, the `getattr` can go. The adapter return in `KVCacheManager.initialize_kv_cache` skips `register_kv_caches`; that is fine while `kv_transfer_config` is rejected, but worth a comment pointing at #1971 so it is not forgotten. And `Qwen4ExpCache.initialize` (typed-owner path) does not precompile `_substitute_placeholder_token` like the pooled path does.

### F6. Core knows the model's name and its `additional_config` schema  [minor, design]  `src/vllm_torchtpu/models/parallel_requirements.py:22-33`, `src/vllm_torchtpu/runner/model_adapters.py:52-61`
`requires_dp_collectives` hard-codes `("Qwen4ExpForCausalLM", "Qwen4ExpForConditionalGeneration")` and the `additional_config["qwen4_exp"]["engram_config"]["embedding_across_dp"]` path; `select_model_adapter` hard-codes the same names. Both are reached from process-binding code (`__init__.py:602`, `tpu_worker.py:198`) so the torch-free constraint is real, but a small registry (`{architecture: predicate}` / `{architecture: adapter factory}` populated from the model package, like `POOLED_GDN_ARCHITECTURES` in `gdn_pool_layout.py`) would keep the next model from editing three core files. The predicate is otherwise general: for non-Qwen models it reduces to `enable_expert_parallel`, exactly the previous rule (`tpu_platform.py:944`, `tpu_worker.py:218/240`, `tpu_rank_binding.py:230`, `tpu_runner.py:3507`).
**Suggested comment:**
> `requires_dp_collectives` and `select_model_adapter` both hard-code the Qwen4Exp architecture names and the `engram_config` key path in core. Could these be registries keyed by architecture (as `POOLED_GDN_ARCHITECTURES` already is), so a future model-owned adapter does not touch `parallel_requirements.py`, `model_adapters.py` and the worker binding? Behaviour for every other model is unchanged either way.

### F7. `splitting_ops` preservation relies on vLLM ordering that the test does not exercise  [minor]  `src/vllm_torchtpu/platforms/tpu_platform.py:765`
Previously the hook unconditionally set `splitting_ops = []`; now it only does so when `None`. This is correct iff `CompilationConfig.set_splitting_ops_for_v1()` (which fills in the attention-op default when `None`) runs *after* `current_platform.check_and_update_config` - true in the vLLM I know (`VllmConfig.__post_init__`, "Do this after all the updates to compilation_config.mode"), but if that ever moves, every existing model would silently switch from a whole-graph compile to piecewise at attention ops. `test_check_and_update_config_preserves_declared_splitting_ops` (tests/platforms/test_tpu_platform.py:924) only builds `VllmConfig()` with `model_config=None`, where that code path is not reached. The `fuse_rope_kvcache_cat_mla = False` addition (tpu_platform.py:790) is presumably because a non-empty `splitting_ops` flips an upstream fusion default; the PR does not say.
**Suggested comment:**
> The `if compilation_config.splitting_ops is None` change is right as long as upstream's `set_splitting_ops_for_v1()` keeps running after the platform hook (otherwise every model would inherit the attention-op split list). Could the test also cover a config with a model (so `VllmConfig.__post_init__` reaches `set_splitting_ops_for_v1`) and assert `splitting_ops == []` for a non-Qwen model and `["qwen4_exp::host_lookup"]` for Qwen with `cpu_offload`? Also a one-line comment on why `fuse_rope_kvcache_cat_mla` is now disabled would help.

### F8. Pooled-mode `state_slots` is a dead argument and `block_size` is read before the executor finalises it  [minor]  `src/vllm_torchtpu/models/vllm/qwen4_exp/inputs.py:97-102`, `:58`
In pooled mode `prepare_inputs` passes `state_slots = arange(rows)` masked to -1, but both consumers replace it: `Qwen4ExpQSA.forward_with_indices` (qsa.py:495-510) takes `state_slots` from `per_layer[prefix + ".raw_ring"].block_tables` and the PLE layer takes `per_layer[ple.prefix].mamba_state_indices` (model.py:168-172); only GDN reads the forward context itself. The arange is harmless but misleading ("Stable slots are neither batch rows nor page IDs" in `QSAMetadata`'s docstring is exactly what this value is not). `self.block_size = runner.cache_config.block_size` (inputs.py:58) is read in `load_model`, before vLLM sets `cache_config.block_size` to the resolved scheduler block (`lcm(layout.block_size, max_model_len)` without APC, per `test_native_pool_preserves_prefix_alignment_and_qsa_owner_aliases`); it happens to read the pool block size, but `dummy_run`'s `pages_per_req` should use `layout.block_size` / the group's kernel block size explicitly.
**Suggested comment:**
> In pooled mode `state_slots` from `prepare_inputs` is never used (QSA and PLE both re-read their per-layer tables from the forward context), so the `arange(rows)` is a decoy - consider passing the ring table / `-1` row mask explicitly or dropping it from the pooled kwargs. And `self.block_size = runner.cache_config.block_size` is read at `load_model` time, before the engine resolves `cache_config.block_size` (which becomes `lcm(block, max_model_len)` without APC); using `layout.block_size` directly would make the dummy page tables independent of that ordering.

## Questions for the author
- APC + ring: with `enable_prefix_caching` the GDN and PLE `MambaSpec`s are seeded through `_build_mamba_copy_plan` (pooled_cache.py:145), but the QSA ring/tags are a `CircularBufferSpec` ("non-cacheable lifecycle"). A hit is always a multiple of the pool block (3200/1664, multiples of `ratio`), so the tail group is empty at the hit boundary - is that the invariant that makes an un-seeded ring safe, and is there a hit-vs-miss equality test like the Kimi one cited in `gdn_pool_layout.py:30-31`? The GSM8K run had APC off.
- How many `kv_cache_groups` / `kv_cache_tensors` does the pooled planner produce for the real 48-layer, 1-PLE geometry? `test_qwen4_exp_cache.py:130` shows 39 groups (TP1) for the typed-owner specs; the pooled test does not assert a count. Each group is a `BlockTable` staged per step and an `AttentionMetadataBuilder.build` per chunk, so the number matters for decode step time.
- Async scheduling: I traced `_modify_prev_results` (runs in `sample_tokens`, tpu_runner.py:4879) and agree the host rows below `context` are committed when `begin_step` runs, so `ngram_context` never sees the placeholder; `test_async_history_reads_committed_prefix_after_reorder_and_row_reuse` encodes that. Was the GSM8K run with async scheduling on or off? (If F1 is fixed with a host-side gather this ordering must be preserved - worth an assert on `token_ids_cpu[row, context-1] != placeholder`.)
- `Qwen4ExpForCausalLM.requires_raw_input_tokens = True` (model.py:300): nothing in the TPU runner reads it; is it for upstream vLLM's `_get_model_inputs`, and does it matter for this text-only model?
- `tpu_compiler.py:425-426` adds `enable_prefix_caching` and `mamba_cache_mode` to the compilation hash. For existing models APC does not change the compiled graph, so this invalidates every user's persistent compile cache once on upgrade; is that intended, or could it be keyed only when an adapter is selected?
- Why is `dummy_run` asserting `input_batch.num_reqs == 0` (inputs.py:139) rather than tolerating live requests like the generic `_dummy_run`? Every current caller (profile, capture, DP idle) satisfies it, but `_warmup_handoff_forwards`-style future callers would trip it.

## Test coverage assessment
CPU-runnable: `tests/runner/test_qwen4_exp_cache.py` is the strongest piece - it drives the real vLLM planner, `KVCacheManager` exhaustion/reuse and the real `AttentionMetadataBuilder` against `Qwen4ExpCache` (typed-owner path) for TP 1/2/4/8, two KV dtypes and three contexts. `test_qwen4_exp_pool.py` checks `pooled_cache_specs` geometry, prefix alignment and that main/compressed/ring land in the same raw tensor, but `Qwen4ExpPooledCache.allocate` (the HBM check in F3 and `materialize_kv_cache_tensors`) is stubbed in every test. `test_qwen4_exp_inputs.py` covers `prepare_inputs`, `dummy_run`, the idle-DP protocol and the async-placeholder ordering with namespace runners. `test_tpu_platform.py` covers `splitting_ops` retention only for `model_config=None` (F7). The "native prefill routing and pool ownership" test (`test_qsa_prefill_routing.py`) is honest about its seam: it runs the real `_prepare_inputs` + builders + adapter and, on TPU, the real pooled op in direct and fullgraph modes with live/inactive cache-row checks - but the "pool" is a hand-built JAX array with hand-picked page ids for one layer; `Qwen4ExpPooledCache`, the dummy-page partitioning, GDN and PLE owners and the scheduler are not involved, so it proves "the adapter hands the pooled QSA op the right tables", not pool ownership across owners. Gaps: no test allocates the pooled cache through `materialize_kv_cache_tensors` (even on CPU with small pages), no APC hit-vs-miss equality test, no DP-lockstep test with a real `Qwen4ExpPooledCache.dummy_metadata` (only the ring-padding shape check), and the full-model numbers (GSM8K 96.51 %) are from an earlier head (`c051187ed`) with APC off and sync/async unspecified.
