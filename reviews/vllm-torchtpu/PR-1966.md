## What it does
`kernels/qwen4_exp/ple.py` adds three pure-JAX pieces for the PLE layer: `compact_rows`/`resident_lookup_raw` gather n-gram embedding rows from a 128-lane "compact" table (rows not padded to lanes, group-based segment indices to stay in int32, owner masking for TP row ranges, 8-token `lax.map` chunks), `decode_embeddings` turns the int16/int8 carrier back into BF16 (bitcast) or FP8 x global scale, and `short_conv` is a dilated depthwise causal convolution over a ragged batch that reads/writes a per-request history window `[slots, state_len, C]`. `kernels/qwen4_exp/pool.py` adds `read_region`/`write_region` (typed per-request reads and id>0-guarded Pallas DMA writes of a token range in the native attention-shaped pool, using #1964's `region_rows`) and `pooled_short_conv`, which runs `short_conv` with identity slots on history read from the pool and writes back only active owners. The model-side wrappers (`ple_op.py`), storage and planner arrive in #1967/#1968; the torch reference `dilated_short_conv` already on main (`models/vllm/qwen4_exp/ple.py:177`) remains.

## Recommendation
REQUEST CHANGES - the convolution and pool I/O logic is sound (ownership, padding and multi-token window update all check out against main's torch reference and upstream's `ple_conv`), but the whole lookup/decode half of `ple.py` has zero tests despite the PR body claiming resident BF16/FP8 lookup coverage, `short_conv` is only compared with itself, and the tap alignment silently depends on an unvalidated `state_len == (K-1)*dilation` contract.

## Findings (ordered by severity: blocker > major > minor)

### F1. Lookup/decode code is untested and the convolution has no independent oracle, contrary to the PR body  [major]  `src/vllm_torchtpu/kernels/qwen4_exp/ple.py:10-94`; `tests/kernels/test_qwen4_exp_ple_pool.py:9-18`, `:78-116`
The test module imports only `short_conv`, `pooled_short_conv`, `read_region`, `write_region` and #1964's `read/write_ring_and_tags`. `compact_rows`, `resident_lookup_raw`, `decode_embeddings` and `resident_lookup` (85 of the 166 lines of `ple.py`) are never executed, yet the PR body says "Tests cover resident BF16/FP8 lookup" and "exercise carrier encodings". The "carrier" the tests vary is the pool dtype of the ring/tag DMA test, not the embedding carrier. The one PLE test (`test_pooled_ple_matches_private_state_and_preserves_other_pages`) compares `pooled_short_conv` against `short_conv`, which it calls internally (`pool.py:89-98`), so the conv math (tap order, dilation, zero-history, window shift, `length > state_len`) is never checked against anything independent. A CPU oracle exists on main: `models/vllm/qwen4_exp/ple.py:dilated_short_conv` (torch, validates the window shape), and all of `ple.py` is plain `jnp`, so these tests can run on the CPU shard. Of the "24 TPU cases", only 4 touch PLE code and 6 use `read_region`/`write_region` as a reference; the remaining 14 test #1964 kernels (see F5).
**Suggested comment:**
> The description says the tests cover resident BF16/FP8 lookup and carrier encodings, but `compact_rows`, `resident_lookup_raw`, `decode_embeddings` and `resident_lookup` are never imported by the test module; the only "carrier" varied is the pool dtype of the ring/tag test. And `test_pooled_ple_...` compares `pooled_short_conv` with `short_conv`, which it calls internally, so the conv math has no independent reference. Could you add CPU tests (everything here is plain jnp): (1) `short_conv` vs main's torch `dilated_short_conv` + silu on a mixed batch with `has_initial_states` true/false, an empty request, trailing padding, a request longer than `state_len`, dilation 1 and 3; (2) `compact_rows`/`resident_lookup_raw` vs a numpy gather for `head_dim=320` (gcd 64, both lane offsets), `head_dim=128`, a 2-way owner split, and `-1` padding ids; (3) `decode_embeddings` FP8 vs upstream's `emb.to(bf16) * scale.to(bf16)` and BF16 bit-exactness through the int16 carrier.

### F2. `short_conv` tap alignment silently assumes `history.shape[1] == (taps - 1) * dilation`  [major]  `src/vllm_torchtpu/kernels/qwen4_exp/ple.py:130-144`; `src/vllm_torchtpu/kernels/qwen4_exp/pool.py:72-86`
`distance = state_len - tap * dilation` (line 133) takes `state_len` from the history array, not from the weight. If a caller passes a window that is not exactly `(K-1)*dilation`, the taps shift with no error: with `weight (C, 4)`, `dilation=3`, `state_len=12` the taps read `x[t-12], x[t-9], x[t-6], x[t-3]` and `x[t]` never contributes; with `state_len=6` the last tap has `distance = -3`, so `position = relative + 3 >= 0` selects `current = x[t + 3]`, a future token that may belong to the next request (non-causal leak across request boundaries). `pooled_short_conv` takes `state_len` as an independent static argument (`pool.py:81`, and #1967 passes a config-derived `conv_state_len`), so the two can drift. Main's torch reference raises on exactly this (`models/vllm/qwen4_exp/ple.py:200-206`); upstream `ple_conv` derives `state_len = (K - 1) * dilation` from the weight (`nvidia/ops/ple.py:593`).
**Suggested comment:**
> `short_conv` derives the tap distances from `history.shape[1]` but never checks it equals `(weight.shape[-1] - 1) * dilation`. With a 4-tap weight, dilation 3 and a 12-row window the taps become `x[t-12..t-3]` (x[t] dropped); with a 6-row window the last tap reads `x[t+3]`, i.e. a future token possibly from the next request. The torch reference on main raises on this and upstream derives `state_len` from the weight. Please add `assert history.shape[1] == (weight.shape[-1] - 1) * dilation` (static shapes, free), and in `pooled_short_conv` either derive `state_len` from the weight or assert the passed value.

### F3. `write_region` is a third typed per-request pool writer  [minor]  `src/vllm_torchtpu/kernels/qwen4_exp/pool.py:30-69`
`pool_adapters.scatter_region` (`kernels/pool_adapters.py:327-410`) already implements the typed per-request token-range write (same `region_rows`-style geometry, aliasing, chunking, lane split), and #1964's `qsa_state.write_ring_and_tags` already implements the `indices > 0` skip with batched DMAs. `write_region` reimplements the DMA + `pl.when` skip with its own VMEM scratch and `typed_ldst.store_typed`, so the kernels/qwen4_exp folder now owns two writers and the shared folder a third, with three places to fix when the pool geometry changes. Not a correctness problem (the ring/tag test shows byte equality with `write_ring_and_tags`).
**Suggested comment:**
> `write_region` duplicates `pool_adapters.scatter_region` plus the `id > 0` skip that `qsa_state.write_ring_and_tags` also has. Could it be expressed on top of `scatter_region` (e.g. remap idle ids to a scratch page, or add an optional `skip_null` to the shared helper) so the pool-geometry logic lives in one place?

### F4. `resident_lookup_raw` is a serial `lax.map` over 8-token chunks  [minor]  `src/vllm_torchtpu/kernels/qwen4_exp/ple.py:59-71`
`jax.lax.map(gather, padded.reshape(-1, 8, heads))` lowers to a sequential scan: an 8192-token prefill runs 1024 dependent iterations, each gathering `8 * heads` rows of 2-3 segments, in every PLE layer. The docstring justifies it with "unbounded full-table gathers failed in the original FP8 lowering probes", but nothing bounds the cost or lets a caller trade it (e.g. `jax.lax.map(..., batch_size=...)`, or a larger static chunk for prefill). No measurement is given.
**Suggested comment:**
> `lax.map` over 8-token chunks is a sequential loop: 1024 iterations for an 8192-token prefill per PLE layer. Was the 8-token chunk measured on TPU7x, and would `lax.map(..., batch_size=N)` or a prefill-sized chunk keep the lowering that worked while cutting the loop count? A one-line number in the PR would settle it.

## Questions for the author
- The body says "duplicated kernel math has been removed", but the convolution now exists twice: torch `dilated_short_conv` on main (still called by `models/vllm/qwen4_exp/ple.py:552` in this head and in #1967) and JAX `short_conv` here. Is the torch one going away in #1967/#1968, or kept as the CPU reference? If kept, a cross-test (F1) is the cheap way to pin them together.
- Speculative decoding: `short_conv` stores the last `state_len` rows of the chunk before acceptance is known (`ple.py:152-159`), and upstream keeps a `state_len + spec_query_len - 1` window for rollback (`nvidia/ops/ple.py:593-600`). MTP is paused, so this is fine now; is the plan to widen the region or to re-run the conv on accepted tokens?
- `pooled_short_conv` treats `ids > 0` as active and `read_region` reads page 0 for idle rows (`pool.py:22`, `:87`); the planner must therefore reserve page 0 as the null page for this pool. Where is that guaranteed (#1968), and is it worth an assert on `ids.min()`?
- `resident_lookup_raw` returns `int8` for any non-int16 table (`ple.py:56`), while #1967's storage keeps the FP8 table as `uint8`; the bitcasts make this harmless today, but should the carrier be the table dtype's unsigned/signed twin explicitly so a future `uint16` table does not silently become `int8`?

## Test coverage assessment
Verified by reading: `short_conv` matches main's torch `dilated_short_conv` semantics (same `back = history - tap*dilation` taps, same window shift `positions = len - state_len + arange`, zero history when `has_initial_states` is false, empty requests dropped via out-of-range scatter, padded tokens masked by `valid`, requests longer than the window take their final `state_len` tokens), and FP8 decode matches upstream's `emb.to(bf16) * scale.to(bf16)`; `pooled_short_conv` only writes `ids > 0 & non-empty`, so empty or padded rows never touch another owner's region, and the TPU test checks byte preservation of pages 0,1,2,4,6 including the null page. What the TPU tests prove: typed pool read/write round-trips for BF16 and FP8 pools with 128 and 10240 channels, pooled == private conv on one mixed batch (dilation 3, window 9), and (for #1964 code) ring/tag DMA, pooled QSA continuation, main-cache writer and block-sparse prefill. What remains uncovered: all of `compact_rows`/`resident_lookup_raw`/`decode_embeddings`/`resident_lookup` (no test at all), the conv math against an independent reference, dilation 1, `length > state_len` and `length == 0` with `has_initial_states=True`, the `state_len` contract of F2, and anything on the CPU shard.
