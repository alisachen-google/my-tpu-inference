## What it does
Two independent Qwen4Exp QSA perf changes under `kernels/qwen4_exp`, both consumed by `pooled_qsa_step` / `qsa_step` (the ops behind `qwen4_exp::pooled_qsa`). Commit 1 lets the composed StreamIndex `BF16KeyReader` accept an FP8/uint8 carrier whose storage row (256) is wider than the query head_dim (128): the DMA window stays full width, the VMEM read slices `[:, :width]` so the MXU contraction and the top-k scoring only use the 128 logical features; the pooled *decode* indexer path (`select_chunk`) stops zero-padding the query for carriers. Commit 2 adds `decode_prefix(starts)` (count of leading one-token requests in the ragged `query_start_loc`, computed on device) and uses it in two places: the pooled indexer's prefill/mixed bucket now passes `distribution=[n_dec, n_dec, num_seqs]` so StreamIndex runs its batched decode schedule for the decode prefix, and `qsa_attention` in a prefill-sized bucket runs the decode prefix through the unchanged batched RPA and the remaining rows (shifted down by `count`) through the block-sparse prefill kernel, then re-interleaves the outputs. KV/compressed/ring/tag writes are untouched and still precede the single indexer call and the single attention entry point. A benchmark script and TPU tests (one decode row in a mixed bucket; logical-width reader equivalence) are added.

## Recommendation
NEEDS DISCUSSION — the dispatch logic, ordering invariant and token-order restoration are correct, but the owner cache is now threaded through a `lax.cond` whose RPA branch aliases it in place (the author's own "emitted cache-owner copies" remark hints at a full-pool copy), the headline "FP8 caller passes the logical query" is only true for the pure-decode bucket, and the mixed path is only tested with exactly one decode row.

## Findings (ordered by severity: blocker > major > minor)

### F1. Owner cache routed through `lax.cond` with an in-place RPA inside the branch — possible full-pool copy per layer per step  [major]  `src/vllm_torchtpu/kernels/qwen4_exp/qsa_rpa.py:231-273`
Before this PR the prefill bucket called `block_sparse_gqa_attention` directly (a read-only kernel, no `input_output_aliases`; it returns `cache` untouched at `block_sparse_gqa_prefill.py:548`), so the donated pool never passed through a conditional. Now `qsa_attention` (lines 266-273) wraps both arms in `jax.lax.cond` on a traced predicate and returns `(output, owner)` from the cond. Inside the `split` arm, `rpa_attention` → `wrapper.ragged_paged_attention` → `kernel.py:1011-1016` aliases the KV cache operand to its output, i.e. an in-place custom call on a *conditional branch parameter*, and the branch root returns that aliased buffer. XLA copy insertion generally cannot let a conditional branch write in place into the conditional's operand buffer (the operand is still live for the other arm and for the result), so the usual outcome is a copy of the whole `pool` before/inside the branch. The PR body says exactly this for the standalone benchmark: "These standalone compilations include emitted cache-owner copies, so the numbers do not establish HBM savings". For the unified pool (the entire main+compressed+ring KV pool, sized to fill HBM) a copy per QSA layer per mixed step would double peak HBM and add a full-pool memcpy to every mixed step; in the pure-decode bucket (line 228-229) and the pure-prefill arm this cannot happen, which is why the benchmark's pure cases look flat.
Failing scenario: any mixed step (`len(query) > max_num_seqs`, `0 < count < starts[-1]`) on the real model with `donate_argnums=(10,)` in `qsa_op.py:123` — check the post-optimization HLO for a `copy` of the pool operand feeding the `conditional`.
Note that neither arm actually mutates the cache (`skip_kv_update=True` at `qsa_rpa.py:112`; prefill kernel is read-only), so the owner does not need to go through the cond at all.
**Suggested comment:**
> `qsa_attention` now returns the owner from a `lax.cond` whose `split` arm runs the batched RPA, which aliases the KV cache in place (`batched_rpa/kernel.py:1011`). Before this change the prefill bucket never put the donated pool through a conditional. Your PR text already mentions "emitted cache-owner copies" in the standalone build — can you attach the optimized HLO (or an XProf memory view) from the full model showing that no copy of the pool is emitted around this `conditional` on a mixed step? If a copy is there, that is a full-pool memcpy per QSA layer per mixed step and doubles peak HBM. Since neither arm writes the cache (`skip_kv_update=True`, prefill kernel is read-only), the simplest fix is to keep the owner out of the cond: return only the attention output from the cond and return the function's `cache` argument unchanged; or hoist the RPA prefix call out of the cond (with `decode_lengths` zeroed when `count == 0`) and cond only the prefill part. Note also that with `count == 0` the shifted call degenerates exactly to the unshifted one (`ids == rows`, `starts - 0 == starts`), so the cond may not be needed at all if an always-on RPA prefix call is acceptable for pure-prefill steps — worth measuring against the 1.3% pure-prefill cost you already pay.

### F2. Commit 1 only applies to the pure-decode indexer bucket; the prefill/mixed indexer path still pads the FP8-carrier query to the 256-wide storage row  [major — claim/code mismatch, no correctness impact]  `src/vllm_torchtpu/kernels/qwen4_exp/pooled_qsa.py:543` (vs `:507-511`)
`select_chunk` (lines 507-511) passes the 128-wide query for carriers, so `prepare_q_inputs` keeps `head_dim=128` and `BF16KeyReader.read` slices `[:, :128]`. The `len(query) > len(context)` path (line 543) still does `jnp.pad(query, ..., width - query.shape[-1])` unconditionally, so for the FP8 carrier `head_dim` becomes 256, `read(..., width=256)` returns the full row, and every prefill step (and, after commit 2, every decode row inside a mixed bucket) still contracts over 128 zero query features against the padding half of each key row. The PR body says "the FP8-carrier caller passes the logical query" — only one of the two callers does. The benchmark's prefill baseline also pads, so the index column of the table says nothing about commit 1 for mixed/prefill (the PR acknowledges the table measures dispatch only). The reader itself is correct: the DMA window keeps `cache_kv_hbm_ref.shape[-1]` (streamindex_topk.py kv_spec), `values.reshape(rows, ref.shape[-1])[:, :width]` slices at a 128-lane boundary, the scale `q.shape[-1] ** -0.5` uses the logical dim in both paths, and the `prefill=True` case of `test_bf16_view_wider_storage_preserves_score_bits_and_owner` proves the 128-wide query works in the MIXED schedule — so there is no technical reason for line 543 to pad.
**Suggested comment:**
> Line 543 still pads the query to the carrier's 256-lane storage row, so the prefill/mixed indexer path (which now also carries the decode prefix) scores the full width; only `select_chunk` (507-511) uses the logical width. Unless there is a reason I'm missing, apply the same `pool.dtype == jnp.bfloat16` conditional here (the `prefill=True` case of the new reader test already proves the 128-wide query is valid under the MIXED/prefill schedule), and re-run the pure-prefill index row of the benchmark with the baseline arm pinned to the padded query so the table actually shows the width change. If you prefer to leave it for a follow-up, please reword the PR body ("the FP8-carrier caller" → "the decode-bucket caller").

### F3. Mixed-bucket dispatch is only tested with exactly one decode row; the batched decode pass and the capacity-sized RPA prefix are untested  [minor]  `tests/kernels/test_qwen4_exp_qsa_rpa.py:330-333`, `tests/kernels/test_qwen4_exp_ple_pool.py:119-124`
Both new TPU lifecycle cases use `first_query=1` with a two-request harness, so `count == 1`. That exercises `decode_batch_end = 0` only (`streamindex_topk.py` `_common_path`: `distribution[0] // 8 * 8`), i.e. the un-batched remainder decode pass, never the `decode_req_batch_size=8` batched pass that commit 2 is meant to reach; and `rpa_attention(query[:capacity], ...)` runs with `capacity == 2`, never the `jax.lax.scan` chunking that kicks in when `max_num_seqs > rpa_query_batch_size` (64 for a 513-column table). The 8/32-decode cases exist only in `scripts/benchmark_qsa_mixed.py`, which asserts exact top-k ids but only `< 1%` per-row relative L2 on attention, and is not a test. `test_decode_prefix_counts_only_leading_one_token_requests` (CPU) covers the counter well, including `[]`, `[0,0]`, `[1,4,1,0]`.
**Suggested comment:**
> The new mixed tests only cover `count == 1`. Could you add a direct TPU test of `qsa_attention` against `_prefill_attention` (or the state reference) with the decode prefix in {2, 8, 9, 65} and a capacity above 64 (so `rpa_attention` takes the scan path and StreamIndex takes the batched `decode_req_batch_size=8` pass plus remainder)? The benchmark covers 8/32 but with a 1% tolerance and outside pytest. Boundary cases `count == 0` and `count == starts[-1]` in a prefill-sized bucket (both must take the plain prefill arm) are worth one assertion each too.

### F4. Prefix RPA call is sized by `max_num_seqs`, not by the decode count  [minor / question]  `src/vllm_torchtpu/kernels/qwen4_exp/qsa_rpa.py:235-244`
`rpa_attention(query[:capacity], ...)` always processes `capacity = len(starts) - 1` rows; with the production `max_num_seqs` (256 in the GSM8K run's DP8 config?) and a 513-column page table, `rpa_query_batch_size` is 64, so every mixed step launches a 4-chunk RPA scan even when there is a single decode row. Zero-length rows are cheap inside RPA, but the per-launch cost is paid regardless. The benchmark pads capacity to `max(8, next_pow2(reqs))` (≤ 64 for every case), so this cost does not appear in the table.
**Suggested comment:**
> The decode prefix RPA runs over all `capacity` rows (4 scan chunks at `max_num_seqs=256`), independent of `count`. Can you add a benchmark row with `capacity=256` and a small decode count (e.g. 1 decode + 128 prefill) so we see the worst-case overhead of the split for a lightly mixed step? If it is significant, a `lax.cond` on `count <= 64` (or trimming the RPA input to the first `rpa_query_batch_size` rows when `count` is small) would bound it.

### F5. Compiled program growth: the prefill kernel is traced twice per bucket and nests another `cond`  [minor / question]  `src/vllm_torchtpu/kernels/qwen4_exp/qsa_rpa.py:249,269` + `block_sparse_gqa_prefill.py:538-543`
Both cond arms call `_prefill_attention`, each of which contains its own `lax.cond(run_aligned, run_with_padding)`, so a mixed bucket now compiles up to four block-sparse prefill programs plus the RPA scan per QSA layer, versus two before. The PR reports a successful full-model run but no compile-time or program-size delta.
**Suggested comment:**
> With the outer cond, each prefill bucket now carries four `block_sparse_gqa_prefill` instantiations (2 arms × aligned/padded) per QSA layer. Do you have the compile-time / executable-size delta for the full model across the token buckets? If it is noticeable, F1's suggestion (no cond; the shifted call is the identity when `count == 0`) also halves this.

## Verified (no action needed, recorded so the reviewer does not re-derive it)
- Runner ordering invariant holds: `tpu_runner.py:1508-1573 _reorder_batch_for_rpa` (called unconditionally at `:3709`) partitions requests with `num_scheduled_tokens == 1` to the front (`segment()` at `:1535-1540`), then spec-verify windows, then prefill/mixed; `maybe_order_prefills_by_kv_len` only permutes within the non-decode tail. Padded inactive rows repeat the last `query_start_loc` (diff 0) and stop the `cumprod`. So `decode_prefix` equals the runner's own `num_decode_reqs` by construction.
- One-token prefill chunks (1-token prompt, last chunk of length 1) are classified as decode — by the runner too — and this is semantically harmless: a single query token attends to its selected groups + partial tail identically in RPA and in the block-sparse kernel, and StreamIndex applies the same `QSAIndexSchedule.positions` offset in the DECODE (`streamindex_topk.py:1676`) and MIXED (`:539`) paths.
- MTP / spec decode: verify windows have ≥ 2 tokens, so `decode_prefix` stops at the first one and they go to the prefill kernel (the pre-PR behaviour). No regression; no gain.
- Zero decodes → `count == 0` → plain prefill arm. All decodes in a prefill-sized bucket → `count == starts[-1]` → plain prefill arm (pre-PR behaviour; the PR explicitly declines an all-decode bypass).
- Split is a traced value; both arms have static bucket shapes (`query[:capacity]`, gathers with clamped `ids`), so no recompilation per count. Restoration (`qsa_rpa.py:246-264`) is a correct permutation: a pure-Python simulation over `[1,1,128,0]`, `[1]*8+[128]`, `[1,4,1,0]`, `[1,1,5,3]`, `[1,2,1]` reproduces the identity on token ids with the padding mask. Shifted `starts = max(starts - count, 0)` yields leading zero-length requests, which `block_sparse_gqa_attention` handles (`searchsorted(..., side="right")` at `:507`, `real % query_block == 0` for empties at `:539`), and the shift is exactly what keeps the aligned arm valid.
- Ring/tag/compressed/main-cache writes happen exactly once and before the single `select_blocks` and single `qsa_attention` calls (`pooled_qsa.py:627-669`, `qsa_rpa.py:317-336`); the split only touches attention.
- VMEM window: kv BlockSpec keeps the storage width; `validate` now allows `shape[-1] >= width` for carriers while native BF16 keeps equality (`indexer_components.py:30-38`). `width % 128 == 0` is guaranteed by `prepare_q_inputs`.
