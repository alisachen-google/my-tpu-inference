## What it does
Adds `vllm_torchtpu/models/vllm/qwen4_exp/hyperconnection.py`, a `GatedResidual` subclass of upstream vLLM's `vllm.models.qwen4_exp.common.hyperconnection.GatedResidual` that keeps the checkpoint parameter structure (hc_norm / input_mix_weight_down / input_mix_weight_up / block_inject_weight) but moves the elementwise math to the BF16/FP32 boundaries used by the NVIDIA Triton kernels (`vllm/models/qwen4_exp/nvidia/ops/hc.py`): BF16 projections, FP32 divide-then-SiLU, FP32 sigmoid, gated mean and residual injection with a single final BF16 cast. It optionally dispatches full-tile, rank-2, BF16 inputs to the #1961 Pallas custom ops (`build_full_mix_op` for norm+gate+mix, `build_gated_residual_op` for combine), with admission computed once at construction from `current_hc_hardware()` (returns None unless `torch.tpu` is already initialized) and static resource checks (`supports_full_mix` / `supports_residual`). `prefill_full_tile` defaults to 0 (off); `prefill_combine_tile=None` inherits it. The model (`qwen4_exp/model.py`) still instantiates the upstream common class; wiring this subclass in is deferred to #1968. The new test file covers CPU numerics against an author-written reference, dispatch/fallback routing with mocked hardware, rank-fallback, and three TPU-marked tests (one of which runs the fused ops at 128/256/384 tokens, eager and `torch.compile`).

## Recommendation
APPROVE WITH NITS. The numerics match the upstream NVIDIA kernels (verified line-by-line against `nvidia/ops/hc.py`), the kernel contracts and tile math line up with #1961, all 14 earlier comments are genuinely fixed in the head, and the remaining issues are a small admission-guard gap on a non-production shape plus test/logging polish.

## Findings (ordered by severity: blocker > major > minor)

### F1. Combine admission still lets rank-2 broadcast / mismatched-token operands reach the kernel  [major]  `src/vllm_torchtpu/models/vllm/qwen4_exp/hyperconnection.py:157-167`
The rank guard added in 08bd9bc4 checks `ndim == 2` for `hyper_input`, `block_output` and `hyper_input_normed`, and checks token count / tile divisibility only on `hyper_input.shape[0]`. It never checks that the three operands agree on dim 0. `gated_residual_fn.core` (kernels/qwen4_exp/gated_residual.py:63-73) requires `block.shape == (tokens, hidden)` and `gates.shape == (tokens, branches)` and raises `ValueError` otherwise, and the `register_fake` in `vllm_adapter.py:58-60` returns `residual.new_empty(residual.shape)` without validating, so under `torch.compile` the fake trace passes and the error only surfaces when the JAX side traces.

Failing input (fused combine admitted, mocked or real hardware, tile 128): `hyper_input` (128, 512) bf16, `block_output` (1, 128) bf16, `hyper_input_normed` (128, 512) bf16. All guards pass (rank 2, 128 >= 128, 128 % 128 == 0, bf16), `_prefill_combine_op` is called with block (1,128) -> `ValueError("Residual merge requires full BF16 tiles and FP32 gates")`. Same for `hyper_input_normed` (1, 512) -> injection (1, 4) != (128, 4). The upstream Torch class broadcasts both of these fine, and the PR body / 08bd9bc4 commit message claim "valid vector, higher-rank and broadcast inputs retain the ordinary Torch layer behavior". The new rank tests (`test_hc_combine_rank_fallback_matches_reference`) only use rank-1 or rank-3 broadcast partners, never a rank-2 leading-1 operand, so they cannot catch this.

Production call sites (`model.py` decoder layer) always pass equal token counts, so this is a contract gap rather than a serving bug, but the whole point of the guard was to be a safe filter in front of the kernel's contract. Two extra conjuncts fix it.

**Suggested comment:**
> The rank-2 guard still admits a rank-2 operand that broadcasts along tokens. With `hyper_input` (128, 512), `block_output` (1, 128), `hyper_input_normed` (128, 512), bf16, tile 128, every conjunct here is true and `_prefill_combine_op` gets a (1, 128) block, which `gated_residual_fn.core` rejects with `ValueError` (and the fake impl does not catch it, so under torch.compile it shows up only at JAX trace time). The upstream Torch `combine` handles that broadcast. Could we add `block_output.shape[0] == hyper_input.shape[0] and hyper_input_normed.shape[0] == hyper_input.shape[0]` to the admission (the `mix` path is fine because `norm` is derived from `hyper_input`), and add a rank-2 `(128, 2) / (1, hidden) / (128, 2)` case to `test_hc_combine_rank_fallback_matches_reference`? That makes the admission a true subset of the kernel contract, which is what the PR text promises.

### F2. Requested fusion that is silently not admitted leaves no trace  [minor]  `src/vllm_torchtpu/models/vllm/qwen4_exp/hyperconnection.py:62-88`
When an operator sets `prefill_full_tile=128` (or a combine tile) but `current_hc_hardware()` returns None (torch.tpu not initialized yet, unknown device kind) or `supports_full_mix` / `supports_residual` rejects the geometry/VMEM budget, the layer quietly keeps `_prefill_*_op = None` and runs the Torch path forever. Nothing is logged and nothing on the module says which path is active. Given that the benchmark in #1961 shows small-N regressions and the flags are explicit opt-ins, an operator who turns them on has no way to tell whether they took effect without reading private attributes. This matters more once #1968 plumbs the tiles through config.

**Suggested comment:**
> When a nonzero tile is requested but admission fails (hardware None because `torch.tpu` was not initialized at construction, unsupported chip, or the VMEM estimate), the module silently stays on the Torch path. Could we `logger.warning_once` (or at least `info`) with the reason when `prefill_full_tile`/`prefill_combine_tile` is nonzero and the corresponding `_prefill_*_op` ends up None? Otherwise someone enabling the flag in #1968 cannot tell from logs whether the fused path is actually live.

### F3. Tile admission vs. runner buckets: document that the tile must divide every compile size, and that decode batches are admitted too  [minor]  `src/vllm_torchtpu/models/vllm/qwen4_exp/hyperconnection.py:35-36,112-116`
Admission is `N >= tile and N % tile == 0` on the padded token count. The TPU runner compiles one static graph per bucket (`torch.compile(backend="tpu", fullgraph=True, dynamic=False)`, buckets from `_get_token_paddings` in `platforms/tpu_platform.py:1297`), so the Python branch is fine for compile. But the consequence is per-bucket: with the default exponential buckets (16, 32, ..., 128, 256, 512, ...) tile 128 admits every bucket >= 128, whereas tile 256 falls back for any linear/extra bucket such as 384 or 640 (`TPU_TOKEN_BUCKET_LINEAR` / `TPU_TOKEN_BUCKET_EXTRA`), and a decode step with 128 padded requests also takes the "prefill" path. None of this is a bug, but the `prefill_` name and the docstring suggest otherwise, and #1968 will pick a tile without this constraint written down.

**Suggested comment:**
> Since admission is purely `N >= tile and N % tile == 0` on the padded bucket, a tile only pays off if it divides every compile size the runner uses (default exponential buckets: fine for 128; any linear/extra bucket like 384 or 640 silently falls back for 256). It also admits decode buckets >= tile, so `prefill_` in the name is a bit misleading. Could the docstring/arg comment state both facts, and could #1968 validate the chosen tile against `compilation_config.compile_sizes` at startup?

### F4. TPU fused test cannot tell whether the fused branch ran  [minor]  `tests/models/vllm/test_qwen4_exp_math.py:452-479`
`test_hc_tpu_full_mix_and_combine` asserts the ops were built and uses shapes that satisfy the guards, then compares with `assert_metrics` (NRMSE <= 1%, cosine >= 0.999). The fused and fallback paths differ only at FP32-association level, so the tolerance cannot distinguish them; if a dtype guard ever flipped (e.g. a future `.to()` leaving `hc_norm.weight` in FP32), the test would still pass on the Torch path. The eager variant can be made load-bearing cheaply.

**Suggested comment:**
> This test proves the ops are built and that the output is close to the reference, but with NRMSE 1% it cannot tell the fused path from the Torch fallback (they differ by ULPs). For the `compiled=False` arm could we wrap `module._prefill_full_op` / `_prefill_combine_op` in a counting callable and assert each was called once per `run`, and additionally compare the fused output against the same module with tiles 0 at a tight tolerance (say `atol=rtol=2**-7` in BF16 terms)? That turns the test into an actual fused-vs-fallback oracle on hardware.

## Questions for the author
- `_normalize` (L96-106) computes the affine as `values * rsqrt(..) * (1.0 + w)`, while NVIDIA `grouped_gemma_rmsnorm` does `y = x*rrms; y += y*w` and the #1961 `_full_mix` kernel does `normalized + scaled`. All three round to BF16 once, so this only moves FP32-internal rounding, but the PR's claim is "match NVIDIA rounding points"; was the `(1 + w)` form kept deliberately (it is what upstream `GroupedGemmaRMSNorm` does), and do you want the Torch fallback and the Pallas kernel to agree with each other here? One-line change if yes.
- `current_hc_hardware()` relies on `torch.tpu.is_initialized()` being True at model construction in the worker. Under torch_tpu's deferred-eager mode, is that guaranteed before `load_model`, or should #1968 force an allocation the way the test fixture does (`torch.ones(1, device="tpu")`)?
- The guards check dtype and rank but not device. A module built on an initialized TPU worker and then fed CPU tensors (debug/reference paths) would route CPU tensors into `pallas.jax_op`. Is that an accepted "don't do that", or worth a `device.type == "tpu"` conjunct?

## Nits
- `src/.../hyperconnection.py:42-45` – `prefill_full_tile` is validated (multiple of 128 -> `ValueError`) but `prefill_combine_tile` only has to be nonnegative; a combine tile of 24 or 100 silently fails `supports_residual` (`tile % row_alignment`) and falls back. Either validate it the same way (multiple of 16) or say in the docstring that unaligned combine tiles fall back.
- `src/.../hyperconnection.py:52-60` – the lazy imports inside `__init__` are what makes `monkeypatch.setattr(vllm_adapter, "current_hc_hardware", ...)` work in the tests; a one-line comment would stop someone hoisting them to module scope and silently breaking six tests.
- `tests/models/vllm/test_qwen4_exp_math.py:71` – `hc_cuda_source_reference` hardcodes `1e-6` instead of `module.hc_norm.variance_epsilon`; `hc_legacy_common_bf16_reference` (L95-109) hardcodes `4` / `2560`. Harmless with the current fixtures, but the reference is reused by the TPU tests and will drift the first time someone parametrizes eps or geometry.
- `src/.../hyperconnection.py:30` – class docstring says "Match NVIDIA HC FP32 elementwise math"; it would help reviewers to cite the exact upstream file (`vllm/models/qwen4_exp/nvidia/ops/hc.py`: `hc_silu`, `hc_gate_mix`, `hc_combine`) since that is the reference the test file claims to derive from.

## Test coverage assessment
CPU tests (31 selected) exercise: exact BF16 equality of `mix`/`combine` against the author-written `hc_cuda_source_reference` for HC 3 and 4 (so the non-power-of-two FP32 divide is covered), two hand-computed single-element rounding oracles for mix and combine that differ from the legacy BF16 contract, state-dict names, invalid-tile rejection, dispatch/fallback routing for 7 shape/dtype/tile combinations with mocked hardware and stubbed ops, 11 rank/broadcast fallback cases with fail-if-called sentinels, independent combine-only admission, and the "unknown hardware / default off never touches the device" invariant. I verified the reference's rounding points against upstream `nvidia/ops/hc.py` (grouped RMSNorm -> one BF16 store; `hc_silu` FP32 divide+SiLU -> BF16; `hc_gate_mix` FP32 sigmoid*x accumulated per stream then `/HC` -> BF16; `hc_combine` `2*sigmoid(inj/HC)` FP32, `res + block*inj` FP32 -> BF16), so the reference is faithful rather than circular. TPU tests (14, deselected in the reported CPU run and reused from the pre-rank-guard head rather than rerun) cover eager and fullgraph-compiled chains at 3/43 tokens on the Torch path, a negative-SiLU oracle, the fused full-mix+combine at 128/256/384 tokens, and a residual-only tile-32 case with HC 3. Gaps: (a) the fused TPU test cannot distinguish fused from fallback (F4); (b) no rank-2 leading-1 broadcast case (F1); (c) no coverage that `torch.tpu.is_initialized()` is True at real worker construction time, i.e. that the fused path is ever admitted in serving, which is deferred to #1968 along with any end-to-end numbers; (d) the author states the rank-guard head was not re-benchmarked or re-run on TPU, relying on an AST-equivalence argument, which is reasonable for four added conjuncts but should be re-run once before #1968 merges.
