## What it does
Adds a `conv_state_dtype` (BF16 or FP32, default BF16) that is threaded from a new `VllmGatedDeltaNetAttention(pooled_conv_state_dtype=...)` constructor kwarg into `get_state_dtype()`, the pool state plan (`_build_v3_pool_state_plan` -> `pooled_gdn_conv_state_bytes(dtype=)` -> `pool_adapters.v3_state_source(conv_state_dtype=)` -> `StateRegion.view_dtype`), the local/sharded pooled runners, both pooled PCP prefill entrypoints, and the shared custom-op cache key. It sits in the RFC #1955 stack as the "pooled-state contract" that #2005 (input preparation) and #1968 (Qwen4Exp model, which passes `pooled_conv_state_dtype=torch.float32`) build on. Recurrence math is untouched; all existing GDN models keep the BF16 conv default because no code path other than the kwarg changes `_pooled_conv_state_dtype`.

## Recommendation
REQUEST CHANGES — the kernel-side plumbing is correct and well tested, but the PR breaks the "single source of truth for pool bytes" invariant that `gdn_pool_layout.py` and the layer's own comment rely on: the block-slot derivation, the Raiden pool manifest (and in #1968 the spec normalizer) still resolve the conv dtype to the BF16 default, so an FP32 declaration only works by padding luck and would be transferred incorrectly by P/D.

## Findings (ordered by severity: blocker > major > minor)

### F1. Block-slot derivation and Raiden manifest still budget/describe the conv region as BF16; new comment claims otherwise  [major]  `src/vllm_torchtpu/layers/adapter/custom_ops/gdn_attention_op.py:512-519`, `src/vllm_torchtpu/gdn_pool_layout.py:64-68`, `src/vllm_torchtpu/platforms/tpu_block_size_utils.py:262-285`, `src/vllm_torchtpu/distributed/kv_transfer/raiden/pool_manifest.py:547-555`
`get_state_dtype()` now declares `self._pooled_conv_state_dtype` to vLLM and the comment at 512-519 says "the block-slot derivation budgets the page from the same explicit conv state dtype". It does not: `tpu_block_size_utils.py:282` calls `pooled_gdn_state_dtypes(dtypes)`, which unconditionally returns `DEFAULT_POOLED_GDN_CONV_STATE_DTYPE` ("torch.bfloat16", `gdn_pool_layout.py:68`), and the comment at 262 still says "Conv remains fixed BF16". The Raiden manifest does the same at `pool_manifest.py:547` and additionally calls `pooled_gdn_conv_state_bytes(...)` at 553 *without* the new `dtype=` argument. The module header at `gdn_pool_layout.py:50-54` promises "every consumer of pool bytes must take its dtypes and sizes from here so no two consumers can disagree"; after this PR the kernel state plan can disagree with both other consumers.

Concrete numbers for the Qwen3.8 geometry the PR tests (local conv_dim 10240, taps 3, SSM 48x128x128 BF16, 1024-byte FP8 token rows): BF16 conv -> 64 conv tokens, 1600 total; FP32 conv -> 128 conv tokens, 1664 total. The derivation computes 1600 and only reaches 1664 because `_align_block_to_backend` rounds up to a kernel-block multiple; `_build_v3_pool_state_plan` (`gdn_attention.py:826-831`) then succeeds by coincidence. For a geometry where the BF16 budget already lands on a block boundary, the first forward raises "GDN state does not fit in the unified pool manager block" (loud, at least). The silent case is P/D: with FP32 declared, `_pooled_gdn_regions` publishes a `_PooledView` for conv with `dtype=bf16, nbytes=num_blocks*61440` (half the live bytes), so a Raiden transfer of an FP32-conv pool moves half the conv rows and reinterprets them as BF16 on the receiver. #1968's `kv_cache_spec_normalizer._pooled_physical_mamba_spec` also retypes the spec back to BF16 via the same helper, so the follow-up does not resolve this either.

**Suggested comment:**
> `pooled_gdn_state_dtypes()` (`gdn_pool_layout.py:64-68`) still forces the conv dtype to `DEFAULT_POOLED_GDN_CONV_STATE_DTYPE`, and both `tpu_block_size_utils.py:282` and `pool_manifest.py:547/553` still size the conv region from it (`pool_manifest.py:553` does not even pass the new `dtype=` to `pooled_gdn_conv_state_bytes`). So after this PR the kernel plan can use FP32 while the page budget and the Raiden manifest describe BF16, which is exactly the contradiction the comment at `gdn_attention_op.py:512-519` warns about — and that comment now states the opposite of what the code does. For Qwen3.8 TP1 this only works because 1600 tokens rounds up to 1664; for P/D the manifest would publish a BF16 view of half the conv bytes. Could we make the conv dtype a single fact that all three consumers read (e.g. `pooled_gdn_state_dtypes(dtypes, architecture)` backed by a per-architecture table that the layer also uses to initialise `_pooled_conv_state_dtype`, or have the layer refuse to construct when `pooled_gdn_state_dtypes((conv, ssm))[0] != conv`), pass `dtype=` in the manifest, and fix the two comments? At minimum an assertion in `_build_pooled_gdn_op` that the declared dtype matches what the derivation budgets would turn the silent case into a startup error.

### F2. Two unrelated knobs now decide the pooled conv dtype; vLLM's `--mamba-cache-dtype` is silently ignored  [minor / design]  `src/vllm_torchtpu/layers/adapter/custom_ops/gdn_attention_op.py:377-381`, `:511`
`super().get_state_dtype()` already resolves a conv dtype from `cache_config.mamba_cache_dtype` (auto -> model dtype) and that value is what `get_mamba_state_dtype_from_config` hands to the block-slot derivation; the pooled branch discards it in favour of the constructor kwarg. A user passing `--mamba-cache-dtype float32` with a pooled GDN model gets BF16 conv storage with no warning, while the model code gets a private second knob. This is the root of F1; resolving the dtype once (either honour the vLLM knob when it is bf16/fp32, or have the architecture table in F1 feed both the layer and the derivation) would make the override visible and consistent.

**Suggested comment:**
> `get_state_dtype()` overrides the conv dtype that `super()` resolved from `cache_config.mamba_cache_dtype` with the constructor kwarg, so the vLLM-facing option is silently ignored for pooled models while the derivation still sees the class-level value. Should the pooled conv dtype be derived from one place (the same place `tpu_block_size_utils` reads) rather than a per-instance kwarg? If the kwarg stays, please document that `--mamba-cache-dtype` has no effect on pooled GDN layers.

### F3. FP32 doubles `conv_tokens`, which can trip the single-kernel-block restriction for small-token-row pools  [minor / question]  `src/vllm_torchtpu/kernels/pool_adapters.py:571-577`
`v3_state_source` raises `NotImplementedError("conv region partially straddles kernel blocks")` when `row0 + conv_ntok > block_size`. `conv_tokens` is the next power of two that covers `conv_bytes`, so FP32 doubles it (e.g. 64 -> 128 for Qwen3.8 at 1024-byte rows). For seq-along-lane pools with a 128-token kernel block and a small payload (the HND layout the new `test_seq_on_lane_fp32_conv_state_plan` uses has 1024-byte rows, where conv fits), a wider conv_dim or narrower token row would now cross the block boundary. Pre-existing limitation, but the PR makes it twice as easy to hit and neither the docstring nor a test covers it.

**Suggested comment:**
> With FP32 conv the power-of-two `conv_tokens` doubles; for a seq-along-lane pool with 128-token kernel blocks that makes the "conv region partially straddles kernel blocks" `NotImplementedError` at `pool_adapters.py:571` reachable for geometries that fit in BF16. Worth a note in the docstring (and ideally a CPU test that asserts the error shape) so the next person who flips a model to FP32 knows what the failure means.

## Test coverage assessment
CPU tests cover the state-plan view dtype (FP32), kwarg forwarding through both pooled ops, op-cache separation by (conv, ssm) dtype, `get_state_dtype()` declaration, and the dtype converter's accept/reject behaviour. TPU tests (not run in CI) compare the pooled FP32-conv/BF16-SSM path against the dense kernel over 4096/8192-token prefill plus three decode steps, and both PCP entrypoints against the non-PCP baseline for a new FP32-conv/BF16-SSM case, including a gather-back of the conv and SSM regions — this is good evidence that the kernel view, byte accounting and plan agree for FP32 on the Qwen3.8 geometry. What is not covered: the engine-level contract (block-slot derivation, `MambaSpec` page cover, Raiden manifest) with an FP32 declaration — precisely where F1 lives — and any non-Qwen3.8 geometry in FP32. The stated test plan proves kernel-level correctness, not that an FP32-declaring model can start or be P/D-transferred.
