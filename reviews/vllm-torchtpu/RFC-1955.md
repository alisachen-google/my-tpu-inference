# RFC #1955: [Qwen4Exp] Native TPU Model Support and Prefill/Decode Disaggregation

- Author: zhubin086. Opened 2026-10-14, last edited 2026-10-23. No labels, no maintainer approval yet.
- Thread: BirdsOfAFthr asked nine questions on 2026-10-15; the author answered the same day; anthonsu agreed with the boundaries on 2026-10-19 and started per-PR review; Nanfang-Li asked on 2026-10-22 for #1968 to be split six ways.
- Link: https://github.com/vllm-project/vllm-torchtpu/issues/1955
- Reviewed against the PR heads of 2026-10-23 (restacked since the per-PR notes in this folder; see "Stack state" at the end).

## What it proposes

Native TPU support for Qwen3.8 Flash through a "Qwen4Exp" architecture: HyperConnection with the upstream NVIDIA BF16/FP32 rounding points, QSA sparse attention composed on top of the DeepSeek-V4 StreamIndex indexer with a block-sparse prefill kernel and a fused TPU7x decode kernel, GDN recurrent layers with a typed input-preparation contract, FP8 MoE on the existing path, and PLE n-gram embeddings extending #1974 with resident or shared-host tables. The model owns its input and cache planning through optional runner adapters. Raiden P/D disaggregation follows, initially DP8/TP1/EP8 with FP8 unified KV, APC off and MTP off. Fourteen PRs are listed with dependencies; MTP, PCP, DCP/PP and broader PD are follow-ups.

## Recommendation

NEEDS DISCUSSION before sign-off. The extension boundaries are the right ones and the component split is real, but the RFC as written no longer matches the stack it describes in four places that affect the design, not just the table: the mixed-batch dispatch it promised is gone, the GDN convolution-history precision was silently changed from the checkpoint's FP32 to BF16 to make the pool accounting consistent, the integration PR has absorbed three component PRs and now needs a core-seams PR of its own, and the PD section describes contracts that #1971 only partly implements while the known cross-host mismatch is unexplained. None of these block the independent component PRs; they do block treating the RFC as the approved design.

## Findings

### R1. Mixed prefill/decode steps run entirely through the prefill kernel; the RFC thread says otherwise  [major]
The author's answer to question 4 on 2026-10-15 was that #1969 "splits one-token requests and prefills into the existing RPA and block-sparse schedules". #1969 was closed on 2026-10-22 without a comment, it is not in the RFC's dependency table, and the current #1968 head (a805066bf) has no trace of it: `kernels/qwen4_exp/qsa_rpa.py:156` routes the whole bucket to `adaptive_prefill` / `block_sparse_gqa_attention` whenever `len(query) > len(starts) - 1`, and to `plan_decode` / RPA otherwise. The docstring right above it now says the threshold "is a static scheduling heuristic, not a semantic mode classifier". So in steady-state serving, every decode request that shares a step with any chunked prefill pays the prefill kernel (the #1969 PR body measured that kernel at 3.1 ms per call for 32 decodes + 512 prefill tokens versus 0.23 ms after the split). The GSM8K number in #1968 was produced at TP8/DP1 with 5-shot prompts and does not exercise this. The RFC should either restore a mixed-dispatch item (and say which PR carries it) or state the serving cost of not having one.
**Suggested comment:**
> Question 4 was answered with #1969, but #1969 is now closed and the current #1968 head routes a bucket by `len(query) > request capacity` only (`qsa_rpa.py:156`), so a step with one chunked prefill plus N decodes sends all N decodes through the prefill kernel. #1969's own measurement put that at ~13x the per-call cost of the split. Is the split coming back in another PR, or is the RFC's serving story "prefill-heavy steps dominate, accept it"? Either answer is fine, but the RFC should say which, because the fused decode kernel in #2123 only helps steps that contain no prefill at all.

### R2. GDN convolution history changed from FP32 to BF16 without an RFC update or an accuracy comparison  [major]
#1963's original purpose was "Qwen3.8 Flash uses FP32 convolution history with BF16 SSM storage, matching the format supported by the non-pooled TPU path" (PR body, 2026-10-14). The per-PR note on #1963 found that the block-slot derivation and the Raiden manifest still resolved conv to BF16 while the layer declared FP32. The fix chosen (0ff5bbbbd on #1963, a805066bf on #1968, both 2026-10-22/23) removes the FP32 override and stores conv history in BF16 everywhere. That is a precision decision for the model, made in a bug fix: the non-pooled TPU path keeps FP32 conv, the HF checkpoint config implies FP32, and the RFC's design section says nothing about conv dtype (it only discusses SSM "BF16 or FP32"). The author's own validation line reads "the evaluation used the BF16 Conv candidate" with GSM8K 96.82% strict versus 96.51% before, which is within noise of a 1,319-item set and is not an A/B at matched code. Question 5 in the thread (SSM dtype accuracy) was answered with "the runs do not isolate the accuracy impact"; the same is now true of conv.
**Suggested comment:**
> The latest #1963/#1968 heads resolve the pool-bytes inconsistency by storing pooled GDN conv history in BF16 instead of fixing the resolver to honour the declared dtype, and the RFC's design text does not mention conv dtype at all. Since the checkpoint and the non-pooled TPU path keep FP32 conv, could the RFC state the decision explicitly and back it with a matched-code comparison (same head, conv FP32 vs BF16, same prompts) rather than the two GSM8K runs on different revisions? If FP32 conv is wanted later, the pool accounting in `gdn_pool_layout.pooled_gdn_state_dtypes` is the place that needs to honour it.

### R3. The implementation plan table no longer describes the PRs  [major]
As of 2026-10-23:
- #1968 is 67 files, +8345/-1964, and its history contains the whole of #2291 (ex #1964), #2123 (fused decode, not listed as a #1968 dependency in the table), #2005, and the new HC modes from #1961/#1962. Nanfang-Li's split proposal on 2026-10-22 (runner/platform seams on main first; pool geometry, GDN input prep, PLE in parallel; adapter+model; deletions last) is the right shape and matches what the per-PR note on #1968 found: the two core commits are the only part that touches other models and they deserve their own owners and their own CI, especially because the compile-hash key change invalidates every existing compilation cache (the "native-cache CI mismatch" the PR body lists as unresolved is most likely this).
- #1964 was merged into an intermediate branch and replaced by #2291 ("history regrouping only"). The RFC notes this, but the table says #2291 depends on "#2017 + #2018 through the frozen combined base 7a7f95af", i.e. on heads that are not the current #2017/#2018 heads. #2017 was rewritten into one commit (a5b1ed656) and #2018 into five (7d77bc31d, +5832/-906 versus its reviewed head). Reviews on #2291 are therefore reviews of stale copies of those two.
- #1965, #1966 and #1967 were rebased onto `zhubin/qwen4-06-qsa-review`; #1965 and #1966 grew (model weights metadata and cache-tag contracts; a stateless convolution kernel) and #1967 gained TP/DP qualification tests. None of the three has a reviewer comment yet.
- #1969 is closed and absent (R1). #1960, #1959 and #1974 are merged.
The table should carry the current head and base per row, and the "combined review base" sentence should say how a reviewer can tell which version of #2017/#2018 a given base contains.
**Suggested comment:**
> Could the dependency table be refreshed with the current head and base per PR? Right now #1968 contains #2291, #2123 and #2005 outright (67 files), #2291 pins #2017/#2018 at a base that predates their rewrites, and #1969 has disappeared. Nanfang-Li's six-way split for #1968 looks right to me; in particular the runner/platform seams commit should go to main on its own, because its compile-hash change invalidates existing compile caches for every model and needs runner owners.

### R4. "Keep Qwen-specific behaviour in the model implementation" is mostly, not fully, honoured  [minor, design]
The per-PR notes found three places where the boundary leaks, all still present in the current heads: core `models/parallel_requirements.py` and `runner/model_adapters.py` know the Qwen4Exp model name and its `additional_config` schema (#1968 note F6); the `chunk_metadata` contract in #2017 makes every schedule re-implement the StreamIndex step layout, so #2291's schedule already diverges from the shared kernel (#2017 note F2); and `pooled_gdn_state_dtypes` in shared `gdn_pool_layout.py` is where the conv-dtype decision of R2 now lives. The RFC's first open question ("are the adapters the right integration boundaries?") can be answered yes with those three named as the things to tidy before the adapters are declared stable.

### R5. The validation section delegates everything to PRs, and the PRs delegate to each other  [minor]
"Component tests compare numerical results with references" is true for HC (#1962, source-derived reference), the block-sparse prefill (#2018, dense reference) and the GDN state plumbing, but the per-PR notes found no test executing the pooled QSA step, main-cache or compressed-key writers (#1964/#2291), none for the PLE resident lookup and decode (#1966), none for the shared-host table reader (#1967), and none for custom StreamIndex components on decode passes (#2017). Almost every kernel test is `tpu_test`; there is no CPU/interpret path, so CI without TPU admission proves nothing for these. The RFC should state, per component, which reference it is compared against and which test runs on CPU, or say plainly that qualification is TPU-only.

### R6. The PD section promises contracts that need checking against #1971  [see PR-1971.md]
The RFC commits to: peer identity including loaded-weight identity, resolved dtype and both physical page layouts; retention of pages until native transfer completion; dual carriers with shared logical block IDs and per-carrier physical stride; admission limited to DP8/TP1/EP8, CP1/PP1, FP8 unified KV, APC off, MTP off. The note on #1971 in this folder checks each of these against the code and proposes causes for the open blocker ("short-input outputs differ across prefill partitions", a two-token prompt diverging at token index 3 while eleven longer prompts matched). Result of that check: the dual-carrier stride/offset arithmetic and the retention semantics hold for all five native owners, including a one-token producer chunk. Three things do not match the RFC text. The #1971 head (4e0051615) is based on #1968 one commit before a805066bf, so merged as-is it would revert the BF16 conv-history decision of R2. The "peer identity mismatch is refused before transfer" promise is asserted only by tests; no code in this repository performs the refusal. And a new `ValueError` for conflicting group pages sits in the shared Stage-3 connector path (`tpu_connector.py:2562`) where the existing code logs, so it affects every multi-group producer, not only Qwen4Exp. On the blocker itself, the bytes moved are correct, so the most likely cause is numerical rather than transport: a two-token prompt is the only case where every prompt position leaves the baseline's chunked path (position 0 in the prefill engine's one-token chunk, position 1 in the decode engine's single-token step), so GDN decode-versus-chunked kernel differences, recurrent-state rounding at the handoff and different token buckets flip a greedy argmax a few tokens later and are diluted on longer prompts. The decisive experiment needs no Raiden: on one host, compare a two-token prefill against a chunked one-plus-one prefill at FP32 and BF16 SSM. If that diverges at the same index, the blocker belongs to #2005/#1968 kernel-path equivalence, not to #1971. Until then the RFC's claim that the native states "represent the same committed token prefix through scheduling, request reuse and transfer" is unproven and should be listed as a design risk, not a PR-level bug.

## Questions for the author

- What is the serving plan for mixed steps now that #1969 is closed: a replacement PR, the fused decode kernel only, or accept the cost (R1)?
- Was the BF16 conv decision driven by the pool-accounting bug or by a measured accuracy result? Can an A/B at one head be added to #1968 (R2)?
- Which of the 73 single-layer KV cache groups that the pooled planner produces (#1968 note F3) are intended, and has their per-step cost been profiled at concurrency 128?
- Does the compile-hash key change in #1968's core commit explain the "native-cache CI mismatch" listed as unresolved? If so, can it land separately with a cache-version bump?
- The RFC says PD "retains pages until native transfer completion". What releases them if the decode peer dies mid-transfer?
- Has the one-host two-token versus one-plus-one chunked prefill comparison been run? It separates a transport bug from a kernel-path equivalence bug without Raiden.

- "Current PD blocker" paragraph says #1971 "is ready for code review while this end-to-end qualification remains incomplete"; the PR itself says "no TPU or performance tests were rerun" on its rewritten head. One of the two should change.
