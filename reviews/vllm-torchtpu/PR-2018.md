## What it does
Adds two standalone prefill attention kernels for QSA (query attends to a per-query set of selected 4-token KV groups plus its own partial group): a TensorCore kernel (`kernels/qwen4_exp/block_sparse_gqa_prefill.py`) that builds a per-query bitset over KV256 tiles, DMAs each active tile once per 256-query block (as two 128-row "paired" page segments so tiles may straddle 1664-token pool pages) and runs an FP32 online softmax; and a SparseCore kernel (`kernels/sparse_gqa_prefill/grouped.py` + `gather.py`) that gathers each query's selected KV into a compact buffer in 32/64-query microchunks and attends with a diagonal query-ownership mask. `adaptive.py` splits the token bucket into 8192-query chunks plus a bounded remainder and, per chunk, picks TC or SC inside the jitted graph via `lax.cond` on a calibrated cost model over tile-union bounds (`cost_model.py`, `occupancy.py`). `prefill_tiles.py` picks TC tiles from rank-local Q/KV geometry and a relative working-set bound. Nothing in the model path calls these yet; #1964's `qsa_attention` routes to `adaptive_prefill` inside the Q24/KV2/D256/page1664 envelope and to `block_sparse_gqa_attention` otherwise.

## Recommendation
APPROVE WITH NITS — the masking, causal/partial-group handling, padded-slot handling and FP32/BF16 boundaries check out and the three earlier review threads are genuinely fixed in the head; the remaining items are a scalability hazard on the un-chunked general TC fallback (which is exactly the path TP=2 lands on), a tile policy that can hand the kernel a rejected tile, and a metadata-contract asymmetry between the two runtime-switched branches, none of which block this standalone-kernel PR but should be answered before #1964 routes production traffic through them.

## Findings (ordered by severity: blocker > major > minor)

### F1. General TC fallback is un-chunked; SMEM/HBM metadata scale with tokens x context (TP=2 lands here)  [major / question]  `src/vllm_torchtpu/kernels/qwen4_exp/block_sparse_gqa_prefill.py:384-387, 413-415, 471-473` and `src/vllm_torchtpu/kernels/sparse_gqa_prefill/adaptive.py:372, 389`
`adaptive_prefill` bounds everything to 8192-query chunks, but it only accepts Q24/KV2 (adaptive.py:371, 376). Every other rank-local layout — notably TP=2 (Q12/KV1), which the author explicitly validated — is routed by #1964 (`qsa_rpa.py:224-237` on branch pr-1964) to `block_sparse_gqa_attention` with the *whole* token bucket. In that path:
- `active_tiles` (block_sparse_gqa_prefill.py:384-387 / 631-633) is a scalar-prefetch operand, i.e. SMEM, of `nblocks * num_kv_tiles` int32. TPU7x SMEM is 1 MiB per core (`jax/_src/pallas/mosaic/tpu_info.py`, TPU_7X). At 256K context (`num_kv_tiles = 1027`) that is 128 KiB for 8192 tokens, but 1.03 MiB at 65536 tokens and 4.1 MiB at 262144 tokens — the adaptive envelope advertises up to 262144 queries (adaptive.py:372), so the runner's bucket can be that large.
- `block_bits_native` is a full `(tokens, words, 256)` int32 array in HBM (line 380-383 / 630): 71 MiB at 8192 tokens, 2.2 GiB at 262144 tokens x 256K context, plus the `(tokens, words)` scatter intermediate at 361-365 when the bounded branch is not taken.
This fails loudly (Mosaic SMEM/VMEM allocation error or HBM OOM), not silently, but it means the "fall back to general TC" story for layouts outside the calibrated envelope only holds for small buckets. Either `block_sparse_gqa_attention` should chunk like `adaptive_prefill` does (reuse `_write_chunk`'s TC branch, which already works for arbitrary `kv_heads`), or the general path needs a documented and validated token cap that #1964 enforces.
**Suggested comment:**
> `adaptive_prefill` bounds per-chunk metadata to 8192 queries, but every layout outside Q24/KV2 (e.g. TP=2 -> Q12/KV1) is routed by #1964 to `block_sparse_gqa_attention` with the full token bucket. There, `active_tiles` is a scalar-prefetch (SMEM) array of `nblocks * num_kv_tiles` int32 — 1.03 MiB at 64K tokens x 256K context against TPU7x's 1 MiB SMEM — and `block_bits_native` is a `(tokens, words, 256)` int32 HBM array (2.2 GiB at 256K x 256K). Since `is_supported_by_adaptive_prefill` advertises buckets up to 262144, could the general wrapper reuse the 8192-chunk loop (the TC branch of `_write_chunk` already works for any `kv_heads`), or should we document and enforce a token cap for the un-chunked path? Right now TP=2 long-prefill would fail at compile time rather than fall back.

### F2. `get_sparse_prefill_tiles` can return a tile pair that `block_sparse_gqa_prefill` rejects  [minor]  `src/vllm_torchtpu/kernels/qwen4_exp/prefill_tiles.py:102-105` vs `src/vllm_torchtpu/kernels/qwen4_exp/block_sparse_gqa_prefill.py:308-313`
The non-paired fallback returns `kv_tile = ratio * 32` without checking page divisibility. The kernel then requires `max(page, kv_tile) % min(page, kv_tile) == 0` (and, for non-paired tiles, a single DMA per tile at :84, so a tile may not straddle a page). Failing inputs:
- `ratio=8`, page 1664 (the production pool page): `kv_tile=256`, `1664 % 256 = 128` -> `ValueError("Each KV tile must use one selection word or two mask segments")`. The existing test `test_other_compression_ratio_uses_general_tc` only passes because it slices the cache to page 128 (`test_qwen4_exp_prefill_geometry.py:233`).
- page 129 (asserted as a valid policy input in `test_bf16_prefill_unmeasured_shapes_keep_single_word_tiles`): `kv_tile=128`, `129 % 128 = 1` -> same ValueError.
Not production-relevant for ratio 4 / page 1664 or 128, but the policy function claims generality and its tests never run the kernel on the returned tiles.
**Suggested comment:**
> `get_sparse_prefill_tiles`' fallback returns `kv_tile = ratio * 32` unconditionally, but `block_sparse_gqa_prefill` rejects it unless the page size and tile divide each other (:308-313). `ratio=8` with the 1664-token pool page, or any page that is not a multiple of 128, yields a `ValueError` from a tile the policy itself selected. Either validate divisibility in the policy and raise a clear error, or state that the TC path requires `page % (ratio*32) == 0` (and ratio 4 for paired tiles) in the docstring; `test_other_compression_ratio_uses_general_tc` currently sidesteps this by slicing the cache to page 128.

### F3. SC and TC branches have different metadata contracts, and the switch between them is data-dependent  [minor / question]  `src/vllm_torchtpu/kernels/sparse_gqa_prefill/grouped.py:64-66, 75-86, 232-236` vs `src/vllm_torchtpu/kernels/qwen4_exp/block_sparse_gqa_prefill.py:351-357`
TC validates every selection entry: `(blocks >= 0) & (blocks < groups)` anywhere in the row. SC never looks at the IDs' validity: it takes the first `min(lengths // 4, 512)` entries as valid (`count`, grouped.py:65; `selected` 232-236) and derives the page via `selected // 416` with an unchecked table lookup (76-86). A `-1` inside that prefix becomes `(-1 % 416) * 4` = rows 1660..1663 of physical page 0; an ID beyond the table becomes page 0. Those rows are "live" (`token < selected_len`) and are attended with full weight. The contract ("`min(length//4, 512)` unique valid IDs in a prefix, then -1") is documented in adaptive.py:50-53 and the doc, and #1964's indexer (`decode_indexer.py:44`, "completed-group IDs with a -1 suffix") appears to satisfy it, so this is not a bug today. But because `lax.cond(choose, sc, tc)` picks the branch from the *selection pattern* at runtime, any future contract violation produces silently different numerics depending on how dispersed the selections are, rather than a consistent error. A cheap hardening: derive `count` from the data (`jnp.sum(blocks >= 0, axis=1)`) instead of from `lengths`, which equals `min(length//4, 512)` under the contract and degrades gracefully to "attend what is valid" otherwise; range-check `logical < table.shape[1]` in `_interleaved_indices` and route failures to a masked lane.
**Suggested comment:**
> The TC path masks any `-1` / out-of-range entry wherever it appears (`(blocks >= 0) & (blocks < groups)`), while the SC path assumes the first `min(lengths // 4, 512)` entries are valid and does not range-check the page lookup — a `-1` inside the prefix gathers rows 1660..1663 of physical page 0 and attends to them with full weight. The contract is documented and #1964's indexer emits a -1 suffix, so this is fine today, but since the TC/SC choice is made at runtime from the selection pattern, a contract violation would show up as pattern-dependent numerics rather than an error. Would you consider computing `count` from `jnp.sum(blocks >= 0, axis=1)` (identical under the contract) and masking `logical >= table.shape[1]` in `_interleaved_indices`, or at minimum stating in `block_sparse_gqa_attention`'s docstring that `adaptive_prefill` requires the stricter prefix contract?

### F4. Bitset construction uses scatter-add; duplicate group IDs flip the wrong bit  [minor]  `src/vllm_torchtpu/kernels/qwen4_exp/block_sparse_gqa_prefill.py:360-365, 617-622`
`jnp.zeros((words,), int32).at[row].add(weight)` with the same `(row, weight)` twice yields `2 * (1 << k)`, i.e. bit `k+1` set and bit `k` clear (and `1 << 31` twice wraps to 0). So a duplicated group ID both drops the intended group and admits a neighbouring one. The same duplicate in the SC path would instead double-weight the group. Uniqueness is part of the documented contract and `streamindex_topk` returns distinct winners, so this is a robustness note rather than a bug, but the TC docstring (`block_sparse_gqa_attention`, :498) does not state it and the kernel is the general fallback for all layouts.
**Suggested comment:**
> `.at[row].add(weight)` is not idempotent: a group ID that appears twice in a row sets bit `k+1` instead of bit `k` (and `1<<31` twice wraps to 0), so a duplicate silently swaps which 32-group word segment is visible. Uniqueness is in the adaptive contract, but `block_sparse_gqa_attention` is also the general fallback and its docstring does not mention it. Could you either document uniqueness there, or build the bitset from a sorted row with adjacent duplicates invalidated (`s = jnp.sort(selected, axis=1); valid &= s[:, 1:] != s[:, :-1]`)?

### F5. Paired-kernel VMEM headroom is <1 MiB at 256K context and the bitset in-spec block is not in the working-set bound  [minor / question]  `src/vllm_torchtpu/kernels/qwen4_exp/prefill_tiles.py:33-35, 38-52` and `src/vllm_torchtpu/kernels/qwen4_exp/block_sparse_gqa_prefill.py:421-424, 448-459`
The bitset input block `(1, words, native_query_width)` int32 is double-buffered VMEM of `2 * words KiB`; `words` scales with context (`roundup(2 * num_kv_tiles, 128)`), so at 256K context it is 2 x 2176 KiB = 4.25 MiB. The comment says the FP8 Q256 kernel compiles to 61.13 MiB and the cap is `PAIRED_PAGE_VMEM_MIB[256] = 62` (TPU7x: 64 MiB per core). If 61.13 MiB was measured at the 158-page table, there is 0.87 MiB of headroom and any context above roughly 256K + 26K fails to compile; if it was measured at a smaller table, the 256K number is unknown. `_paired_working_set` (38-52) models only Q/accumulator/softmax/KV buffers and ignores this term, so the "relative bound" is insensitive to the one input that varies with context. No wrong numerics are possible here (compile-time failure), but the limit should be stated.
**Suggested comment:**
> The paired kernel's bitset BlockSpec `(1, words, 256)` int32 is double-buffered and `words` grows with context: 4.25 MiB at 256K context. With `PAIRED_PAGE_VMEM_MIB[256] = 62` and a measured 61.13 MiB, what table width was that measured at, and what is the largest context at which Q256 paired still compiles on TPU7x? Since `_paired_working_set` does not include the bitset term, consider either adding `2 * words * native_query_width * 4` to it (so wider tables demote to Q128) or capping `page_table.shape[1]` in `supports_paired_prefill` the way `is_supported_by_adaptive_prefill` does (`<= 158`).

### F6. Bounded metadata path is skipped for FP8 non-paired layouts  [minor / question]  `src/vllm_torchtpu/kernels/qwen4_exp/block_sparse_gqa_prefill.py:328-335`
The `lax.map`-batched `_prepare_metadata_bounded` is used only when `(paired_pages or cache.dtype == jnp.bfloat16) and query_block == 256 and tokens * words * 4 >= 16 MiB`. An FP8 cache on a non-paired layout (e.g. the `ratio != 4` or page-not-multiple-of-128 fallbacks) with a large bucket takes the unbatched `vmap` branch (361-365), materialising the `(tokens, words)` scatter plus its transpose at once. The condition looks like a leftover from when FP8 implied paired; the bounded path is dtype-agnostic.
**Suggested comment:**
> Why is the bounded metadata path gated on `paired_pages or cache.dtype == bfloat16` (:329)? `_prepare_metadata_bounded` does not depend on the cache dtype, so an FP8 cache on the non-paired fallback with a large bucket still builds the whole `(tokens, words)` scatter in one go. Dropping the dtype term seems safe.

## Test coverage assessment
All numerical checks are `tpu_test`; there is no CPU interpret-mode run of either kernel, so the CPU suite only exercises the tile policy, the static envelope checks and the cost-model/occupancy bounds (those are compared against explicit Python tile sets, including partial tails and inactive rows). On TPU the references are independent: a NumPy dense-over-selected-tokens reference for the general TC kernel (`test_qwen4_exp_paired_pages.py:240-269`, ratio 4 and 8, page 128 and 1664, FP8 with non-unit scales), an FP64 row reference in `check_reference` for paired geometry (Q12/KV1, Q8/KV2/D384, Q24/KV3, Q8/KV4 FP8, Q16/KV4/D128, 8448 and 16640 tokens) and for the adaptive path, and an FP64 reference plus TC-vs-adaptive comparison in `test_adaptive_prefill_preserves_mixed_outputs_with_bounded_memory` which asserts the SC kernel is present in the HLO and that per-chunk `select_sc` decisions match `sc_first`, so rows 1/32 in SC chunks are checked against the FP64 reference. Padded inactive slots (length 0, -1 IDs, NaN query/gate, repeated starts, NaN-poisoned unreferenced pages), ragged request boundaries inside a Q256 tile, 17/257-token tails smaller than an SC microchunk, odd 1664-page tails and permuted physical pages are all covered. Remaining gaps: (a) multi-chunk + ragged starts (`_ragged_tc_write` with a nonzero `offset`, and a ragged remainder after a full chunk) is never run on TPU — all >8192-token cases use `starts = [0, tokens]`; (b) no test runs the kernel on every tile pair the policy returns (F2); (c) contract violations (duplicate or out-of-range IDs, `-1` inside the prefix) are untested in both branches (F3/F4), which is acceptable given the documented contract but means the TC/SC equivalence is only established for conforming inputs; (d) the general TC path is never compiled above 16640 tokens, so the SMEM/HBM growth in F1 is unmeasured; (e) the standalone SC test (`test_sparse_gqa_grouped_prefill.py`) compares against the TC kernel rather than an independent reference, but the adaptive FP64 checks close that gap.
