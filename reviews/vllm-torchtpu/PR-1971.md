# PR #1971: [Core][Model][Qwen4Exp] Add Raiden Prefill/Decode Disaggregation
- Author: zhubin086 / head: 4e0051615 / base: zhubin/qwen4-10-model-cache (#1968, now at a805066bf) / size: true delta 26 files +3423/-109 (the 34-file diff against a805066bf includes 8 files of pure staleness, see F1) / state: Draft, no review comments, CI not run on this head; author reports the cross-host mismatch unresolved.
- Link: https://github.com/vllm-project/vllm-torchtpu/pull/1971

## What it does
Adds a model-owned Raiden Stage-3 connector for Qwen4Exp (`Qwen4ExpRaidenConnector`/`Qwen4ExpRaidenWorker`, `pd_connector.py`) on top of the shared `TPURaidenConnector`. Every scheduler cache group becomes a transfer group (`pd.py`): QSA main pages are `TOKEN_PAGES`, while GDN state, PLE state and the QSA raw-key ring are `REQUEST_STATE` groups that transfer exactly one page per request. A manifest (`pd_manifest.py`) binds each live owner (incl. the `compressed_k` alias on the index carrier) to whole physical pages of the two raw carriers (FP8 main, BF16 index) and measures the TPU tiled layout into a fingerprint; `pd_identity.py` hashes every loaded checkpoint tensor and gathers per-rank records (checkpoint, config, FP8 KV scales, SSM dtype, QK-pair flag) into the fingerprint payload. The shared connector gains a `request_state` flag on `_Stage3TransferGroup` plus group-table validation on both producer finish and consumer alloc, and the Qwen config/connector enforce DP8/TP1/EP8, CP1/PP1, FP8 KV, APC off, MTP off only when `kv_transfer_config` is set. The runner now returns the materialized named caches from the model adapter so the connector can register them.

## Recommendation
REQUEST CHANGES. The head is not rebased on its declared base (it silently reverts #1968's BF16 conv-history commit, F1), the new conflict check in the shared scheduler path raises instead of refusing (F2), and the RFC's "peer identity refuses a mismatch before any transfer" is asserted by the tests themselves rather than by any code path in this repo (F3). The transfer contract itself (dual whole-page carriers, all five native owners, retention until native completion) checks out; the blocker analysis (section B) points at the one-token truncation protocol interacting with prefill-vs-step numerics rather than at the transfer code.

## A. Contract check against RFC #1955

**(1) Committed prefix identity.** What is hashed: `LoadedWeightIdentity.observe()` sha256s the raw bytes, dtype and shape of every tensor the loader consumes (`pd_identity.py:27-55`), finished as a whole-checkpoint digest and a `.ple.`-only digest (`model.py:522-523`). `_collect_pd_semantics` (`pd_connector.py:185-230`) adds per-rank: engine-relative rank, tp rank/size, the HF config dict minus path/commit/version, `(layer, k_scale, v_scale)` for every full-attention layer (checked against the CPU buffers), and `state_flags = {gdn_qk_pair, expert_parallel, ssm_dtype, cp:1, pp:1, mtp:False, apc:False}`; the records are all-gathered over the EP group and must agree on config/state_flags/ple digest across ranks (`pd_identity.py:70-99`). The layout half (`pd_manifest.py:150-233`) records, per raw carrier, `shape[1:]`, minor-to-major, tiles, element bits and dtype, plus every pool's tag/storage index/regions/stride/dtype tag, plus `torch_tpu` and `libtpu` versions. Both halves go into one `canonical_layout_fingerprint(dict(layout=..., semantics=...))` (`pd_connector.py:232-245`) that is handed to `register_work_unit(layout_fingerprint=...)` in the shared `_register_raiden_stage3_work_unit` (`tpu_connector.py:3834-3907`). So the RFC's list (loaded-weight identity, resolved SSM dtype, both physical page layouts) is covered, with two caveats: the SSM dtype is the *configured string* (`pd_connector.py:221`), which is only safe because `validate_config` refuses `auto` for PD (`config.py:394`, contrary to the RFC's "auto follows the checkpoint"); and the conv-history dtype is not in the identity at all, which is only safe while it is a compile-time constant on both peers (after the F1 rebase it is `DEFAULT_POOLED_GDN_CONV_STATE_DTYPE`). Whether a *mismatch is refused before any transfer* is not visible in this repo: the only comparison of two peers' fingerprints is in the test (`test_qwen4_exp_pd_transport_tpu.py:200`), i.e. the refusal is delegated to the tpu_sync controller (F3).

**(2) Retention until native completion.** Producer: `request_finished` only publishes for `FINISHED_LENGTH_CAPPED/STOPPED` (`tpu_connector.py:2307-2311`); abort/preempt before finish publishes nothing, so nothing is retained. On publish, `_stage3_publish_send` returns `delay_free_blocks=True`, and vLLM keeps *all* groups' blocks of the request until the worker reports `done_sending`. The worker registers the page spans with the controller with `expiration_time = now + TPU_P2P_WAIT_PULL_TIMEOUT` (120 s, `utils.py:92`, `envs.py:139`). Release paths: native completion (`poll_stats` sent → `complete_request_blocks`, `tpu_connector.py:6855-6878`), TTL expiry with `cancel_request_blocks_if_unclaimed` (`6697-6712`), a consumer-side cancellation observed by the status probe (`_probe_stage3_registrations`, `5319`), or a native sender failure. If the decode host dies *after* claiming, `cancel_..._if_unclaimed` returns False and the pages stay pinned until the native manager reports the failed transfer (`timeout_s` of the KVCacheManager) — that is the shared behaviour, unchanged here, and worth stating in the PR body. New for Qwen: `_stage3_register_ahead_enabled` is forced off for request-state groups (`tpu_connector.py:1614`), so registration always waits for finish (the whole-page plan needs the complete group tables). Consumer: the request stays in `WAITING_FOR_REMOTE_KVS`; `_submit_stage3_loads` snapshots `group_block_ids` so a mutated scheduler object cannot retarget an in-flight load (`5614-5641`). This matches the RFC.

**(3) Dual carriers, shared logical IDs, per-carrier stride.** `materialize_pool` builds one FP8 main carrier `(blocks, block_size, slots, pack, head_dim)` and one BF16 index carrier `(blocks, index_rows//2, 1, 2, width)` per region (`pool_allocation.py:80-96`); `self_attn` and `self_attn.compressed_k` share the block ID (main vs index carrier), `raw_ring` has its own ID on the index carrier, `linear_attn` and `ple` have their own IDs on the main carrier. The PR's pool entries are `block_stride_bytes = raw.nbytes // num_blocks`, `base_offset 0`, one region covering the stride (`pd_manifest.py:106-125`), and `measure_transfer_layout` asserts `num_blocks * stride == nbytes` and `stride % row_bytes == 0` so native tile padding cannot shift pages (`pd_manifest.py:181-199`). Spans are one whole page per block (`src_offset=dst_offset=0, size=stride`, `pd_connector.py:296-304`); destination tags/pages are emitted in manifest order on both sides (`pd_connector.py:311-331`). Owners transferred: QSA main KV (main page), compressed keys (index page at the main ID), ring + tags (index page at the ring ID, incl. the 8-byte tag rows inside the page), GDN SSM + conv (main page of the state ID; the whole page is copied so the BF16-vs-FP32 conv region question is moot for the transfer), PLE conv history (main page of the PLE ID). **Nothing in the pool is skipped**; `build_transfer_manifest` refuses an unreferenced carrier (`pd_manifest.py:128`). Not transferred by design: the last prompt token's state (D recomputes it) and the PLE n-gram token history, which D rebuilds from its own token store (`inputs.py:36-43, 86`). The GDN conv region arithmetic depends on `gdn.dtypes[0]` in the base (`pool_layout.py:83` at a805066bf) but on the stale constant in this head (`pool_layout.py:85` here) — see F1.

**(4) Admission.** `validate_config` (`config.py:383-408`) checks `(TP, DP) == (1, 8)`, EP on, connector name/module, role producer|consumer, FP8 KV, APC off, SSM dtype in {bfloat16, float32}, Raiden transport, no other model's admission; the connector constructor checks CP1/DCP1/PP1/MTP/APC (`pd_connector.py:66-74`); the worker checks transfer parallelism == TP (`pd_connector.py:248-256`). All of it sits inside `if transfer is not None:` so non-PD serving keeps the #1968 ordinary admission — the RFC thread's question 3 is honoured. Missing: nothing refuses `TPU_RAIDEN_STAGE3_REGISTER_AHEAD`-style env combinations explicitly, but they are neutralised in code.

**(5) Core-file footprint.** `tpu_connector.py`: all new branches are gated on `group.request_state` (default False) or on the overridable `_build_stage3_transfer_groups/_supports_stage3_grouped_transfer/_raiden_worker_type/_uses_stage3_grouped_pages` hooks, whose base implementations preserve the DSv4 behaviour; the one unconditional change is the duplicate-finish group check (F2) and the stricter replay checks that now compare `group_block_ids` (`4900-4915`, `5617-5623`). `kv_cache_manager.py`: the adapter path previously returned *before* registering any connector, so this PR adds registration only for adapters, and the non-adapter path is a pure refactor. `tpu_platform.py`/`patch_registry.py`: `_register_tpu_kv_connectors` moves from an explicit call to an `_ENGINE`-stage patch; `platform_activation` is still applied in `check_and_update_config` before the connector-name assert (`tpu_platform.py:684` vs `1051`), so API-server behaviour for TPURaidenConnector is unchanged and worker/engine-core processes gain it. `utils.py` and `gdn_attention_op.py` only differ because of staleness (F1), not because of this PR.

## B. Blocker hypothesis: "short-input outputs differ across prefill partitions" / mismatch at token index 3

Geometry that matters (`tests/models/vllm/qwen4_exp_test_utils.py`): `indexer_compress_ratio = 4`, GDN `linear_conv_kernel_dim = 4` (3 history taps), `ple_conv_kernel_size = 4`, `ngram_size = 3`. Protocol: the producer truncates the prompt by one token at admission (`tpu_connector.py:1138-1157`, forced for Qwen by `request_state` groups, `1582-1591`), so for a 2-token prompt P computes position 0 only, transfers, and D computes position 1 as its first step, then generates. "Token index 3" is therefore either generated token y3 (sequence position 4) or sequence position 3 (y1); both readings are considered below.

(i) **GDN conv / PLE history for a prefix shorter than the window.** Code: GDN history is cut from the padded tile at `compute_conv1d.py:65-68` with a masking loop for shorter sequences; the kernel masks `has_initial_state` from `seq_lens` (`gdn_attention.py:895-899`); PLE `short_conv` masks `past` with `has_initial_states = context_lens > 0` (`ple.py:154,170`, `model.py:173`) and writes `[0,...,0,x0]` for a 1-token chunk (`ple.py:165-171`). I could not find a wrong-slot or zero-initialisation path: on D, `context_lens = 1 > 0` so both read the transferred page. If this were wrong, y0 would already differ because every conv window at positions 1..3 contains x0. Test: single host, no Raiden, run prompt `[p0,p1]` as one 2-token prefill vs. chunked `[p0]` then `[p1]` (set `max_num_batched_tokens=1` or use the chunked-prefill scheduler) and diff the GDN/PLE state pages after position 1 byte-for-byte. Likelihood: low.

(ii) **Ring / compressed key for the incomplete compression group.** Code: `_indexer_updates` (`kernels/qwen4_exp/qsa.py:107-172`) keeps the partial group in the ring, zeroes ring/tags when `context == 0` (`130,158-159`) and consults them when `context > 0`; for a 1-token P chunk it writes lane 0 = k0, tag (pos 0), lanes 1..7 = 0/-1 — exactly what D expects at positions 1..3; the group completes at position 3 (`complete = logical % 4 == 3`, `148`) and c0 is written before `select_blocks`. Position 4 (= generated index 3) is the first query that *reads c0 back from the index page* instead of computing it in-step, which is the only PD-specific event that lines up with "index 3". But with a 5-token context there is one candidate group and `block_topk = token_topk // 4 >> 1`, so a merely *wrong* c0 cannot change the selection; only a NaN/garbage c0 (SparseCore top-k dropping the group) could. The transferred index page at the main block ID is a recycled P page whose compressed rows were never written for this request; `write_compressed` "preserves the other half of partial pairs" (`pooled_qsa.py:296-300`), so the unwritten row 1 of pair (0,1) comes from P's stale data — finite, but worth a check. Test: on D after the first step, dump the index page rows 0-1 of the request's block 0 and the ring page; after position 3, assert c0 equals `rope(norm(mean(k0..k3)), 0)` recomputed on host; also run the 2-token case with `indexer_budget` forced to 4 to make selection sensitive. Likelihood: medium only if NaN can appear; otherwise low.

(iii) **Prefill-partition numerics (my top hypothesis).** "Prefill partitions" reads as: the same prompt positions computed under a different chunking produce different cache contents. The one-token truncation moves position N-1 from the chunked prefill path to D's single-token path for *every* prompt, and for a 2-token prompt it moves *all* prompt positions out of the baseline's 2-token chunk: position 0 is computed as a 1-token chunk on P and position 1 as a 1-token step on D. QSA attention is symmetric (it always reads K/V from the FP8 pool after `write_main_cache`, `pooled_qsa.py:620-631`), but the GDN kernel runs different code paths for 1-token rows vs chunked rows (`distribution` decode/prefill split, `wrapper.py:800-807` BATCHED vs PER_SEQ), the chunked path keeps the recurrent/conv carry in FP32 inside a chunk while PD rounds the SSM state to storage dtype at position 0 (`wrapper.py:505-507`; exact with FP32 SSM, lossy with BF16 SSM), and MoE/HC kernels see different M buckets. Each gives sub-ulp-to-1e-3 differences at positions 0/1 that compound through the recurrent state and flip the greedy argmax a few tokens later; longer prompts dilute the perturbation (only position N-1 moves paths, and logit margins are larger), which is exactly "short inputs differ, 11 longer cases matched". This also explains the author's note that "forcing single-token prefill is not the proposed fix": token-by-token prefill on the baseline would hide the difference. Test (no Raiden needed): one engine, FP32 SSM, greedy, prompt `[p0,p1]`: (a) plain 2-token prefill, (b) chunked prefill 1+1, (c) `max_num_seqs=1` with the prompt submitted as 1 token then continued; compare logits at position 1 and the first 8 generated tokens; repeat with BF16 SSM. If (b)/(c) diverge from (a) at the same index, #1971 is exonerated and the blocker belongs to #2005/#1968 (GDN path equivalence) or to the protocol (consider committing N tokens and having D re-run the last one only for the logits).

(iv) **Decode-first ordering / single-token request treated as decode on D.** On D the first step is a 1-token row with `num_computed_tokens = 1 < num_prompt_tokens`, so vLLM schedules it as a prefill and the input token comes from the prompt, not from a pending async sample; `ngram_context_from_store` gathers `[eos, p0]` from the full D prompt (`inputs.py:36-43`, test at `test_qwen4_exp_pd_connector.py:365-395`). The Qwen runner adapter's placeholder substitution applies to decode rows only, and a wrong substitution would corrupt y0, not y3. On P a 1-token new request also lands in the decode-shaped bucket, which is the same path as (iii). Likelihood: low as a separate cause; it is one of the path differences in (iii).

Most likely: (iii). The transfer code moves the right bytes (verified above); what changes between the baseline and PD is *which kernel path computed the committed positions*, and for a 2-token prompt that is every prompt position. I did not find a definite bug with a failing scenario in the transfer code itself.

## Test coverage assessment
CPU tests cover: group planning and page counts (`test_qwen4_exp_pd.py`), scheduler-side publish/alloc validation incl. state-first group order, bad pages, CP/DCP and partial prefix refusal (`test_stage3_request_state_pages.py`), worker span lowering and replay/conflict checks with a synthetic single-carrier plan (`test_qwen4_exp_pd_connector.py`), manifest binding against a real materialised CPU pool incl. the compressed/ring alias and byte-preserving whole-page copies (`test_qwen4_exp_pd_manifest.py`), local layout measurement (`test_qwen4_exp_pd_layout.py`), checkpoint digest/identity consistency (`test_qwen4_exp_pd_identity.py`), config admission (`test_qwen4_exp_config.py:233`), connector registry/platform wiring and adapter cache registration. The TPU test `test_qwen_all_owner_pages_over_native_reshard` moves synthetic page bytes between two processes on one host through a real Raiden controller for all owner pages and both SSM dtypes, which is good evidence for the carrier/stride contract. Gaps: no test that a peer with a different identity is refused (F3); no test of the producer retention lifecycle end-to-end (TTL cancel, consumer death after claim); no model-level test that the state pages written by a 1-token producer chunk reproduce the baseline when consumed with `context_lens > 0` (the exact scenario of the open blocker); and the stale-head tests (`test_gdn_attention_op.py`, `test_qwen4_exp_gdn_prefill.py`) will conflict on rebase.
