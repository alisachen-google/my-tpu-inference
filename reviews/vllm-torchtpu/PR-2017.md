## What it does
Adds two small modules next to the DeepSeek-V4 StreamIndex kernel: `components.py` (a `KeyReader` protocol that decodes a HEAD_ALONG_SUBLANE VMEM window into `keys[rows, D]` + `scales[1, rows]`, an `IndexSchedule` protocol that remaps query positions, admitted prefix lengths and per-chunk pipeline metadata, bundled in a frozen `StreamIndexComponents`) and `topk_backend.py` (a `TopKBackend` protocol over the int32 score-bit buffers, with `SparseCoreTopK` as the default wrapping the existing `sparsecore_topk` call). `streamindex_topk` gains two trailing static JIT kwargs, `components=None` and `topk_backend=SparseCoreTopK()`; with the defaults the kernel takes exactly the pre-PR code paths. With `components` set, the kernel calls the reader instead of the packed-FP8 unpack in both the generic `step_body` and the blocked-prefill `load_chunk`, applies `positions`/`visible_lengths` in `_effective_row_lengths`, feeds the schedule's per-chunk metadata with `chunk_idx=0`, and always takes `_common_path` (no score-free early exit). The backend's `overlaps_scoring` flag gates the cross-engine TC/SC scheduling-group annotations. This is the extension point that #1964 (Qwen4Exp `BF16KeyReader`/`QSAIndexSchedule`) and #1969 build on.

## Findings (ordered by severity: blocker > major > minor)

### F1. Custom components are never exercised on the decode passes  [major]  `tests/kernels/test_streamindex_topk_backend.py:266`
Every composed-components test builds `distribution = [0, 0, len(seq_lens)]` (`_component_inputs`, line 266) and uses multi-token `q_lens`, so only the MIXED pass (`static_q_len=None`, `seq_batch_size=1`) runs with a reader/schedule. The decode passes — batched decode (`seq_batch_size=decode_req_batch_size`, reader called as `components.keys.read(bkv_vmem.at[batch_idx], bkv_sz, head_dim)` at `streamindex_topk.py:545-547` for `batch_idx > 0`) and single decode (`static_q_len=1`, `n_tok == 1` branch of `reduce_heads` at `:445-450`) — never see a custom reader or `positions()`. That is precisely the path #1964's `select_decode_blocks` uses (`num_queries_per_block=1`, decode sequences). The PR body's "chunked generic/blocked-prefill execution" claim is accurate but does not cover decode.
**Suggested comment:**
> All component tests use `distribution=[0, 0, N]` with multi-token rows, so the reader/schedule only run through the MIXED pass. Could you add one TPU case with leading decode sequences (`distribution=(d, d, N)`, `q_lens` of 1, `decode_req_batch_size>1` so `seq_batch_size>1`) and check it against the same host reference? That covers `components.keys.read(bkv_vmem.at[batch_idx], ...)` for `batch_idx>0` and the `n_tok == 1` reduce path, which is what #1964's `select_decode_blocks` will rely on.

### F2. `chunk_metadata` makes every schedule re-implement the kernel's step layout  [major, design/contract]  `src/vllm_torchtpu/kernels/deepseek_v4/streamindex_topk/streamindex_topk.py:1537-1542`, `components.py:59`
With components, `_scores_for_chunk` passes `components.schedule.chunk_metadata(pass_meta, chunk_idx)` and forces `chunk_idx=0`, so the kernel's own `step_offset = sum(num_steps[:chunk_idx])` (`:261`, `bref_override.py:25-27`) is bypassed and the schedule must reproduce it. The protocol docstring only says "returns one chunk's steps indexed from zero", not that the native arrays hold all chunks back to back in a `max_steps` buffer sized `num_chunks * per_chunk_bound` (`metadata.py:187-200`). Two implementations already exist and already differ: the test's `PrefixSchedule` uses `jnp.take(..., offset + arange(size), mode="clip")`, while #1964's `QSAIndexSchedule` uses `lax.dynamic_slice_in_dim(..., offset, size // num_chunks)`, which is only correct because of the `max_steps` sizing invariant in `metadata.py` (a smaller window or an uneven split would clamp the start index silently; bounds checks are disabled in the kernel). Neither implementation actually changes the schedule — both are identity-on-a-chunk. The hook as specified leaks a kernel internal into every model directory.
**Suggested comment:**
> `chunk_metadata` currently requires each schedule to re-derive the back-to-back step layout (`offset = sum(num_steps[:m])`, window sized from `max_steps`), and the two implementations we have (`PrefixSchedule` here, `QSAIndexSchedule` in #1964) already do it differently — #1964's `dynamic_slice_in_dim(…, size // num_chunks)` only works because `metadata.py` sizes `max_steps` as `num_chunks * per_chunk_bound`. Could the kernel own this instead: add `MetadataRef.chunk(chunk_idx)` (or `metadata.slice_chunk`) in `metadata.py`, call it before handing the chunk to the schedule, and make `chunk_metadata` optional (default identity)? Alternatively keep passing the native `pass_meta`/`chunk_idx` unchanged unless a schedule overrides. Either way the docstring should state the layout invariant the hook must preserve.

### F3. Schedule output reaches the backend unclamped; visibility above causal diverges between scoring paths  [minor]  `streamindex_topk.py:1071-1079`
`positions()` may legitimately shift positions negative (the test uses `-3`; #1964 uses `-(ratio-1)`), so `visible = min(kv_len, token_pos // ratio + 1)` can be `<= 0` before `visible_lengths` runs. Nothing after the hook clamps, so a schedule that does not `max(0, …)` itself hands negative `row_lengths` to the backend (both existing schedules happen to clamp). Conversely, `visible_lengths` is documented as mapping causal to "admitted" lengths with no upper bound, but the generic path still applies the causal mask inside the kernel (`:497`) while the blocked prefill path leaves those columns unmasked (`:642-646`); a schedule that admits more than the causal prefix would therefore score `-inf` on decode and real values on prefill. Cheap to make robust: clamp after the hook and state the `admitted <= causal` requirement.
**Suggested comment:**
> After `visible = components.schedule.visible_lengths(visible)` could we add `visible = jnp.maximum(visible, 0)`? `positions()` can push `token_pos` negative (your test and #1964 both do), and the backend otherwise gets negative `row_lengths` if a schedule forgets to clamp. Also worth stating in the `IndexSchedule` docstring that `visible_lengths` must not exceed the causal input: the generic kernel path still applies the causal mask (`compute_scores`, line 497) but the blocked prefill path does not, so admitting more than causal would give different scores on the two paths.

### F4. `TopKBackend` contract should spell out what lives beyond `row_lengths` and who validates `k`  [minor]  `topk_backend.py:24-34`
The score buffer is deliberately not pre-filled (`_scores_for_chunk`, `streamindex_topk.py:1524-1527`): columns at or past `row_lengths[r]` and whole KV blocks the schedule skipped hold uninitialized memory, not `-inf`. The docstring says "only columns below each row length are eligible; -inf marks invalid scores", which a #1969-style TensorCore backend could read as "mask on -inf". Also, `k` constraints are backend-specific (`sparsecore_topk` requires `k % 128 == 0`, `k <= 4096`; the test's `ReferenceTopK` accepts `k=16`) and `streamindex_topk` does not validate `k`, so a bad `k` for the default backend surfaces only after scoring has been traced. `overlaps_scoring` is really "runs on SparseCore, so the TC/SC group pairing applies" — a TensorCore backend returning `True` would annotate two TensorCore ops.
**Suggested comment:**
> Two contract clarifications for the backends that #1969 will add: (1) please state that `score_bits` columns at/after `row_lengths[r]` (and any KV block the schedule did not score) are uninitialized, not `-inf`, so a backend must mask by `row_lengths` first and may only treat `-inf` as invalid within that prefix; (2) `k` constraints are backend-specific (`sparsecore_topk` needs a multiple of 128, at most 4096) — either a `validate(k)` hook called before scoring, or a sentence in the docstring. A note that `overlaps_scoring=True` means "this backend runs on SparseCore" would also keep a TensorCore backend from setting it.

### F5. `positions()` runs inside the Pallas kernel body  [minor]  `streamindex_topk.py:538-539`, `components.py:42-50`
The hook is applied both in XLA (`_effective_row_lengths`) and on the `q_pos` vector inside `step_body`, so it must be Pallas-traceable on an int32 `[bq_sz]` vector (elementwise only; no gathers, no shape change). The docstring only says "preserves the shape".
**Suggested comment:**
> `positions()` is also evaluated inside the Pallas kernel (`step_body`, line 539), so implementations are limited to elementwise int32 ops; could the `IndexSchedule` docstring say so?

## Test coverage assessment

The TPU cases do test what matters for the kernel plumbing: BF16 keys with explicit scales against an independent NumPy reference, non-identity positions, row-dependent visibility including empty rows, `k > visible` padding, `return_scores` padding, and real chunk boundaries (`chunk_tokens=32` with a 32-token sequence straddling the cut, 512-token sequences spanning four KV blocks, query blocks of 8 and 16).
