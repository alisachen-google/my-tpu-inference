## What it does
Introduces `Conv1DInput`, a frozen-dataclass JAX pytree (`values` = FP32 `[tokens, 1, features]` leaf, `output_dtype` = static metadata) in `kernels/gdn/v3/input_layout.py`, and teaches `fused_conv1d_gdn` to accept either an ordinary array (unchanged `astype(f32)` path) or a prepared `Conv1DInput` (skips the cast, keeps the activation output dtype). The adapter gains a `_prepare_pooled_gdn_input(mixed_qkv, seq_lens, mesh)` hook that returns its input unchanged by default; the override's identity (`type(self)._prepare_pooled_gdn_input`) is added to the shared custom-op cache key. A Pallas BF16->FP32 tile converter plus eligibility predicate live in `kernels/qwen4_exp/gdn_input.py`; nothing in shared code calls them (verified: no `qwen4_exp` import under `kernels/gdn`, `layers/` or `pool_adapters.py`). #1968 subclasses the adapter and wraps the converter in a `shard_map`.

## Recommendation
APPROVE WITH NITS, conditional on rebasing onto the current #1963 head — the default path is provably unchanged, the prepared path is bit-compared against the original path on TPU, and the boundary claim holds; the remaining issues are a latent closure/cache-key hazard, a VMEM envelope that is not enforced, and a benchmark that was not run on this head.

## Findings (ordered by severity: blocker > major > minor)

### F1. Shared op closure now captures a specific layer instance; the cache key only covers the class-level override  [major (latent)]  `src/vllm_torchtpu/layers/adapter/custom_ops/gdn_attention_op.py:767`, `:824`
Before this PR `wrapped_fn` closed over plain values (`mesh`, `vllm_config`, head geometry, dtypes) that are all in the `_get_shared_gdn_op` key, satisfying its contract ("kind and key together must cover every value that the op's kernel and fake capture", line 353-356). Now `wrapped_fn` calls `self._prepare_pooled_gdn_input(...)` (line 767), so the op built for the first layer with a given key is reused by every later layer and dispatches preparation through *layer 0's* `self`. The key (line 824) contains `type(self)._prepare_pooled_gdn_input`, i.e. the function object, which distinguishes subclasses but not instances. Any override that reads instance state (`self.prefix`, a per-layer policy, `self.num_spec`-dependent capacity, etc.) silently uses layer 0's values for all layers. #1968's override is stateless today, so nothing fails now, but the PR's stated guarantee ("a subclass cannot accidentally reuse another preparation path's closure") is only half implemented and the trap is invisible at the call site.

**Suggested comment:**
> `wrapped_fn` now closes over `self` (line 767) while the cache key only carries `type(self)._prepare_pooled_gdn_input` (line 824). Every other layer with the same geometry reuses this op and therefore runs *this* instance's hook, so an override that consults instance state would silently apply layer 0's state to all layers — which is the kind of closure reuse the key was meant to prevent. Could we make the hook explicitly instance-free (a `@staticmethod`/`@classmethod` taking `(mixed_qkv, seq_lens, mesh)`, resolved once outside `wrapped_fn` as `prepare = type(self)._prepare_pooled_gdn_input`), and extend the `_get_shared_gdn_op` docstring to say the hook must be a pure function of its arguments and class? That keeps the key honest without adding instance ids to it.

### F2. `supports_compact_qkv` admits a 24 MiB double-buffer window but the `pallas_call` sets no `vmem_limit_bytes`  [minor / question]  `src/vllm_torchtpu/kernels/qwen4_exp/gdn_input.py:29-35`, `:48-56`
The predicate accepts widths up to `24 MiB / (2*128*6)` = 16384 features; the GDN kernel itself sizes its limit from `vmem_capacity_bytes` (`config.py:247-252`) but the converter uses the Pallas default scoped VMEM limit, which is generation-dependent and on v5e/v6e is below 24 MiB. For Qwen's width 10240 the window is 15 MiB, so the tested geometry fits everywhere; the 12288/16384 cases in `test_compact_qkv_preserves_value_bits` are `tpu_test` and were only run on TPU7x. If the "envelope" is meant to be a correctness guarantee of the predicate, the call should pin `vmem_limit_bytes` (or the predicate should use the real scoped default); otherwise a supported-looking shape fails at compile time on other chips.

**Suggested comment:**
> `supports_compact_qkv` promises the tile "fits its aligned, double-buffered envelope" of 24 MiB, but `compact_qkv_input` relies on the Pallas default scoped-VMEM limit, which is smaller than that on some TPU generations. Either pass `vmem_limit_bytes=` in `CompilerParams` (derived from `window_bytes`, like `GDNConfig.get_vmem_limit_bytes` does for the main kernel) or lower the envelope to what the default guarantees, so the predicate is a real fit check rather than a TPU7x observation.

### F3. `Conv1DInput.output_dtype` is not normalized, so equal dtypes can produce different jit/treedef keys  [minor]  `src/vllm_torchtpu/kernels/gdn/v3/input_layout.py:31`
`output_dtype` is static pytree metadata and therefore part of every `jax.jit` cache key and treedef comparison. Callers pass `qkv.dtype` (a `np.dtype`), but nothing stops `Conv1DInput(values, jnp.bfloat16)` — `jnp.bfloat16` (the scalar type) hashes differently from `np.dtype('bfloat16')` even though they compare equal, which means a redundant recompile and, in `shard_map` in-spec matching (`gdn_attention.py:1003-1006` builds the spec tree from the same object, so that case is safe), a potential treedef mismatch. A `__post_init__` that does `object.__setattr__(self, "output_dtype", jnp.dtype(self.output_dtype))` closes this.

**Suggested comment:**
> Since `output_dtype` is static metadata it is hashed into every jit cache key; `jnp.bfloat16` and `np.dtype("bfloat16")` are `==` but hash differently. A `__post_init__` normalizing through `jnp.dtype(...)` (and rejecting non-dtypes) would make the contract robust for the next caller.

## Questions for the author
- Benchmark: both reports were measured on revisions that are not this PR's head — `106ec6245` (an earlier flag-based design) and the "integrated revision `8d64fa813`", whose script imports `vllm_torchtpu.models.vllm.qwen4_exp.gdn.prepare_gdn_input`, which only exists in #1968. The PR body says so. Can the second script be made runnable on this head (subclass `VllmGatedDeltaNetAttention` in the script, or call `compact_qkv_input` + `Conv1DInput` directly) and re-run once, so the numbers are attributable to this change? My reading of the evidence: the methodology is sound (3 fresh processes, alternating AB/BA, exact output + byte-exact pool equality in both arms, device-time localization of the 244->170 us conversion delta inside an unchanged 1607-1681 us GDN body), and it supports exactly what is claimed — a modest ~3-4% GDN-only wall gain for >=2K-token prefill/mixed buckets and nothing for decode. What it does not establish is whether that ~75 us per GDN layer at 8K tokens is worth a new pytree type, a hook on the adapter and a per-model kernel package once QKV projection, MoE and the rest of the forward are included, or how the `shard_map`-wrapped converter behaves at TP>1 (single device only). I would ask for either an end-to-end number from #1968 or an explicit statement that this is infrastructure for later layout work, before accepting the abstraction on its own.
- The fused PCP projection op (`_build_pooled_pcp_gdn_op`, line 879) never calls the hook, and `run_jax_gdn_attention_pooled_pcp_prefill` / `fused_qkvz_projection_pcp_gdn` are still typed as arrays. Long prefill is where the converter pays off, and long prefill under PCP goes through those paths. Is the prepared path intentionally TP-only, and should the docstring of `_prepare_pooled_gdn_input` say so?
- #1968's policy prepares whenever `tokens > seq_lens.shape[0]`; padded-decode buckets with 8 live requests in a 128-token bucket then convert 120 dead rows and the benchmark shows that is flat-to-slightly-positive. Fine, but worth stating in the hook docstring that it is called per compile bucket, not per live request, so overrides must not branch on traced values.

## Test coverage assessment
CPU: `test_compact_qkv_preserves_value_bits` bit-compares the converter against `astype(f32).reshape` for six fallback shapes (non-128-multiple tokens, width not a multiple of 128, width above the envelope, FP32 input) — on CPU every case takes the fallback branch, so the Pallas kernel itself is only exercised by the five `tpu_test` parameters. `test_pooled_input_preparation_separates_cached_ops` proves the default hook passes the identical object through and that a subclass override yields a distinct cached op (class-level only, see F1); `test_pooled_pcp_wrapper_forwards_state_formats` is #1963 coverage. TPU: `test_prepared_input_preserves_recurrence_and_decode` runs the original and prepared paths through the real `fused_conv1d_gdn` for 128/8192-token prefill plus three decode steps and asserts `assert_array_equal` on output, conv state and SSM state (BF16 and FP32 SSM) — this is the comparison that matters and it is exact, not tolerance-based; the author's benchmark independently asserted exact output and byte-exact pool equality across 42 shape/process combinations. Gaps: no test of the prepared path through `run_jax_gdn_attention_pooled` at TP>1 (the `P(None, None, "model")` in-spec branch at `gdn_attention.py:1001-1006` is untested), no test that `Conv1DInput` survives `pallas.jax_op`/`jax.export` inside the custom op (the adapter tests mock `jax_op`), and the VMEM envelope is only validated on TPU7x.
