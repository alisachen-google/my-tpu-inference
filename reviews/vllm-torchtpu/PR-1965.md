## What it does
Adds `models/vllm/qwen4_exp/qsa.py`, a model-owned attention layer (`Qwen4ExpQSA`, an `AttentionLayerBase`) for the Qwen3.8 Flash "full_attention" layers: it builds q/k/v/o projections, q/k Gemma norms and a replicated MQA indexer (`index_qk_proj`, `q_layernorm`, `k_layernorm`), loads them from `...self_attn.`-relative checkpoint names with shape/dtype validation, maps the twelve upstream KV-scale aliases onto `_k_scale/_v_scale`, computes a padded BF16 RoPE cos/sin table, and publishes the planner contract (`FullAttentionSpec` main KV with head packing, `MLAAttentionSpec` compressed keys, `CircularBufferSpec` ring + int64 tags) plus `get_cache_owner_layouts`/`bind_cache_owners` for four private owners. `layers/adapter/custom_ops/qsa_op.py` wraps #1964's `qsa_step` (and, unused here, `pooled_qsa_step`) as `pallas.jax_op`s with fake impls, donation and `copy_` write-back. It sits between the #1964 kernels and the #1968 model/planner; nothing in this PR allocates the owners or constructs `QSAMetadata`, so the layer is inert until #1968.

## Recommendation
REQUEST CHANGES - the weight mapping, TP sharding and fake-op contract check out against upstream vLLM v0.31.0 and the #1964 kernel, but the layer silently assumes geometry it never validates (indexer_kv_heads == 1, head/TP divisibility) and the PR description claims a metadata builder and geometry-rejection tests that are not in the diff.

## Findings (ordered by severity: blocker > major > minor)

### F1. Kernel geometry assumptions are not validated (indexer_kv_heads, head/TP divisibility)  [major]  `src/vllm_torchtpu/models/vllm/qwen4_exp/qsa.py:162-172`, `:232-244`, `:387-390`
`_Indexer` sizes `index_qk_proj` as `(indexer_n_heads + indexer_kv_heads) * indexer_head_dim` (line 164), but `load_weights` expects `(index_n_heads + 1) * index_head_dim` (line 388) and the kernel's `produce()` (`kernels/qwen4_exp/qsa.py:85-97`) slices exactly one K head (`index_qk[:, -index_dim:]`). With `indexer_kv_heads=2` the module parameter and the expected checkpoint shape disagree and every indexer load fails with the unrelated message "Invalid BF16 QSA checkpoint tensor". Likewise `self.num_heads = total // tp_size` (line 232) and `kv_rank/kv_size` (243-244) are computed without the checks upstream performs (`vllm/models/qwen4_exp/nvidia/qsa.py:300-313`): with 24 heads and tp=16 the 12288-row `q_proj` passes vLLM's `divide()` (768 rows/rank) but `num_heads` becomes 1, so `produce()` reshapes 768 columns into `(n, 1, 512)` and fails at trace time; `tp=3` with 2 KV heads gives `kv_rank=2` for `kv_size=2` and narrows out of range. The test matrix only covers power-of-two TP that divides 24.
**Suggested comment:**
> The kernel only supports one indexer K head (`produce()` slices `index_qk[:, -index_dim:]`), but `_Indexer` sizes the projection with `indexer_kv_heads` while `load_weights` expects `(n_heads + 1)`; with `indexer_kv_heads != 1` both disagree and the user gets "Invalid BF16 QSA checkpoint tensor". Could `__init__` raise explicitly on `indexer_kv_heads != 1`, and also on `num_attention_heads % tp_size` and `tp_size % num_key_value_heads` (upstream nvidia/qsa.py does both)? Today tp=16 with 24 heads passes `divide()` on q_proj (768 rows/rank) and only fails inside the kernel reshape.

### F2. PR body claims metadata construction and geometry-rejection coverage that are not in this diff  [major]  `src/vllm_torchtpu/models/vllm/qwen4_exp/qsa.py:32-49`, `:128-136`; `tests/models/vllm/test_qwen4_exp_qsa.py`
"Build the sparse-kernel metadata from positions, request boundaries and independent owner tables" (PR body, "How") has no implementation here: `QSAMetadata` is a frozen dataclass, `get_builder_cls()` returns the generic shared `AttentionMetadataBuilder`, and the comment at line 130 defers to a "model adapter" that only exists in #1968 (`model.py:186-196`). The commit title "load and execute native sparse attention layers" overstates similarly. On the test side the body says loading rejects "missing or incompatible checkpoint geometry", but only the *missing* path is tested (`match="Missing"`, test line 381); no test feeds a wrong-shape or non-BF16 tensor, no test exercises the `finalize_weights()` success path after a complete load (norm weights are never loaded in any test), and no test is marked `tpu_test`, so the "hardware coverage" paragraph of the test plan selects zero tests from these files.
**Suggested comment:**
> The description says this PR builds the sparse-kernel metadata, but `QSAMetadata` is only a dataclass here and the builder is the generic `AttentionMetadataBuilder`; the construction (and the padded-request contract documented in the docstring) lives in #1968. Please either move that construction + its tests here or reword the "How"/commit title. Also, "rejecting incompatible checkpoint geometry" is not covered: there is no test for a wrong-shape/dtype tensor, and `finalize_weights()` is only tested on the failure path (no test ever loads the norm weights and finalizes). And since none of these tests carry `tpu_test`, the hardware paragraph of the test plan runs nothing from these files.

### F3. `Qwen4ExpQSABackend.get_kv_cache_shape` reports a layout the layer rejects  [minor]  `src/vllm_torchtpu/models/vllm/qwen4_exp/qsa.py:152-156` vs `:342-356`, `:358-367`
The backend returns `(2, num_blocks, block_size, num_kv_heads, head_size)`, while the only accepted owner shape is `(pages, 128, head_slots, packing, padded_dim)` (`get_cache_owner_layouts`), enforced by `bind_cache_owners`. Any caller using the backend's shape (the generic runner allocation path, future P/D manifest code that reads `get_kv_cache_shape`) would allocate something `bind_cache_owners` raises on. `get_impl_cls` already raises for the same reason.
**Suggested comment:**
> `get_kv_cache_shape` advertises `(2, blocks, 128, kv_heads, head_dim)` but the layer only binds `(pages, 128, head_slots, packing, padded_dim)`; either compute the real owner shape here (from the same packing rule as `get_cache_owner_layouts`) or raise like `get_impl_cls` so nobody allocates through the generic path by accident.

### F4. `raw_ring` spec describes a smaller/odder state than the owner that is bound  [minor]  `src/vllm_torchtpu/models/vllm/qwen4_exp/qsa.py:77-81`, `:98-105`, `:242`, `:333-339`
`CircularBufferSpec(block_size=ratio, head_size=index_dim + 8 // 2, head_size_v=0)`: `8 // 2` is 4 bf16 elements standing in for the 8-byte int64 tag (operator precedence makes it read as `(index_dim + 8) // 2`), and `block_size=ratio` (4) while the bound owner has `ring_size = (ratio + 7) // 8 * 8` (8) rows. The spec's unpadded page is `4 * 132 * 2 = 1056 B` at defaults, the actual owner is `8*128*2 + 8*8 = 2112 B`; only `page_size_padded = max(8192, ...)` keeps allocation safe, and `kv_cache_spec_normalizer.py:150-192` treats `page_size_padded` as something it may replace. The `CircularBufferSpec` docstring (vLLM `kv_cache_interface.py:890-898`) also requires `block_size` to exceed the compression ratio by the speculative lookahead; it equals the ratio here (fine while MTP is paused, but worth a comment).
**Suggested comment:**
> The ring spec understates the owner: `block_size=ratio` vs the 8-aligned `ring_size` actually bound, and `head_size=index_dim + 8 // 2` (= +4 bf16 for the int64 tag) is hard to read. Could the spec use `block_size=self.ring_size` and `head_size=index_dim + TAG_BYTES // 2` with a comment, so the unpadded bytes match the owner instead of relying on the 8192 floor in `page_size_padded`? Also worth noting that `CircularBufferSpec` expects `block_size > ratio` once speculative lookahead is enabled.

### F5. Dead code and per-step metadata re-encoding in the op wrapper  [minor]  `src/vllm_torchtpu/layers/adapter/custom_ops/qsa_op.py:83-115`, `:121-165`
`build_pooled_qsa_op` is only used by #1968 (`bind_pool`); nothing here calls it. In `run()`, the int64 `rope_tags` owner is split into two int32 planes (`torch.stack`), passed donated, and recomposed with shifts/ors every forward; six index tensors are also `.to(int32)`-converted per call. The kernel only ever stores `[position, 0]` (`_indexer_updates`, `kernels/qwen4_exp/qsa.py:160-166`), and #1968's pooled layout keeps tags as int32 `(slots, ring, 2)`, so the int64 owner buys nothing.
**Suggested comment:**
> `build_pooled_qsa_op` has no caller in this PR (it lands with #1968) - consider moving it there. Separately, is there a reason `rope_tags` is an int64 owner? The kernel only stores `[position, 0]` and the pooled layout already uses int32 `(slots, ring, 2)`; making the private owner int32 `(slots, ring, 2)` would drop the per-step stack/shift/or and one donation.

## Questions for the author
- Does the released FP8 checkpoint carry `self_attn.indexer.index_qk_proj.weight_scale_inv`? Upstream builds `index_qk_proj` with `quant_config` (`nvidia/indexer_qsa.py:131-137`), while this loader forces `quant_config=None`, requires BF16 and raises on any unexpected name (`qsa.py:412-417`). The base test's `modules_to_not_convert` lists `self_attn.{q,k,v,o}_proj` but not the indexer. If the indexer is quantized in the release, loading will fail here; if not, a one-line note would help.
- Who validates at the torch boundary that `len(query_start_loc) == len(context_lens) + 1 == len(state_slots) + 1 == main_block_table.shape[0] + 1`? `_token_metadata` clamps `req` to `len(slots) - 1` and relies on padded requests being "repeated query offsets + slot -1" (docstring lines 38-39); a cheap static-shape assert in `forward_with_indices` would turn a mis-sized builder into an error instead of silently re-owning tokens.
- `context_lens` is documented as "logical length BEFORE this chunk, independent of positions". On a prefix-cache hit with `context_lens % compress_ratio != 0` and a fresh ring slot (ring zeros, tags -1), the open group's raw keys are gone; is that excluded by the planner in #1968 (ring is `prefix_cacheable=False`, but the main KV is not), or does the next completed group get averaged with zeros?
- `get_kv_cache_spec(vllm_config)` ignores its argument and uses the `cache_dtype` captured at construction. Intentional (so that #1968 can pass `cache_config.cache_dtype` once)?

## Test coverage assessment
The CPU tests (32 cases) cover: the padded RoPE table equals vLLM's `cos_sin_cache` for four rotary dims; the twelve KV-scale aliases update buffer, `_cpu` copy and `_float` consistently and reject non-scalar/non-finite/duplicate scales; owner-layout shapes and the fake-op output shapes for `auto/fp8/fp8_e4m3` under `FakeTensorMode` (so the real op schema is dispatched); exact TP slicing of q/k/v/o/indexer for seven `(tp, rank)` pairs, including KV replication for tp > kv_heads (verified against v0.31.0's `update_param_tp_status`, which is why the global-rank monkeypatch does not interfere); and `bind_cache_owners` rejecting a wrong shape. Verified independently: checkpoint names (`q_proj/k_proj/v_proj/o_proj/q_norm/k_norm/indexer.index_qk_proj/indexer.q_layernorm/indexer.k_layernorm`) match upstream `nvidia/indexer_qsa.py` and `nvidia/qsa.py`; per-head `[q, gate]` interleave matches `Qwen3NextAttention._project_qkv_gate`; Gemma `(1 + w)` norm matches both; `donate_argnums=(10..13)` index the four owners; the fake returns the same count/shapes/dtypes as `qsa_step` (int32 `selected`, BF16 output on both the RPA and block-sparse paths). Gaps: no test marked `tpu_test`, so the layer's forward is never executed on hardware against a dense reference; no test for the "incompatible geometry" rejection path or for `finalize_weights()` after a complete load; no metadata-builder tests (none exists here); `build_pooled_qsa_op` is untested and uncalled; unsupported geometries (tp not dividing heads, `indexer_kv_heads != 1`) are neither rejected nor tested.
