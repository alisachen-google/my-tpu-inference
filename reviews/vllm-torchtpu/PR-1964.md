## What it does
Adds the Qwen3.8-Flash QSA layer on top of the shared StreamIndex scoring/top-k pipeline (#2017) and the standalone block-sparse / adaptive prefill kernels (#2018). `indexer_components.py` supplies the two opt-in components the shared kernel accepts: `BF16KeyReader` (bitcasts a DMA'd FP8/uint8 carrier window to BF16 keys with unit scales) and `QSAIndexSchedule` (shifts query positions by `ratio-1` so only fully completed compression groups are visible, and slices the per-chunk scalar-metadata window). `decode_indexer.py` / `pooled_qsa.select_blocks` drive the shared kernel with per-token expanded tables for decode and the native ragged request batch (BQ128, 512-token chunks) for prefill. `qsa_rpa.py` turns the selected groups plus the partial tail group into "virtual pages" of size `ratio` for the existing batched RPA (decode) and routes multi-token steps to #2018's adaptive/TC kernels; `qsa.py` holds the projection/RoPE/pooling math and the ring/tag (raw key + RoPE position) updates. `pooled_qsa.py` + `qsa_state.py` are the production variant where main KV, compressed keys, ring and tags all live in one donated pool, written through aliased Pallas DMA kernels. This is the layer that #1968 (runner/pooled op) sits on.

## Recommendation
REQUEST CHANGES - the arithmetic I could check is right (completed-group visibility, chunk windows, pair ownership, virtual-page construction), but the production pooled path (~1k lines of aliased DMA kernels: `pooled_qsa_step`, `write_main_cache`, `write_compressed`, `read/write_ring_and_tags`) is never executed by any test in this PR, the request-vs-token padding heuristics that pick prefill vs decode are fragile in both directions, and all three of anthonsu's threads are still open in the head.

### F1. The pooled (production) path has zero test coverage in this PR  [major]  `src/vllm_torchtpu/kernels/qwen4_exp/pooled_qsa.py:590`
`pooled_qsa_step` (pooled_qsa.py:590), `write_main_cache` / `_write_main_cache_universal` (134/45), `write_compressed` with its three Pallas kernels incl. the FP8-carrier read-modify-write of BF16 pairs (273), `read_ring_and_tags` / `write_ring_and_tags` (qsa_state.py:26/88), `region_rows` and both tuned-batch lookups are not called by any test (`grep -rn pooled_qsa|qsa_state|write_compressed|ring_and_tags tests/` only hits `test_qwen4_exp_prefill.py:188-199`, which calls `select_blocks` with `streamindex_topk` monkeypatched to a fake). The only end-to-end lifecycle test (`tests/kernels/test_qwen4_exp_qsa_rpa.py:186`, `_check_lifecycle`) drives the non-pooled `qsa_rpa.qsa_step`, whose cache writers are plain `.at[].set` scatters. The PR body's "native paged ownership" / "cache-byte preservation" coverage belongs to #1968, so this PR ships the most intricate code (aliased `input_output_aliases`, VMEM-resident DMA indices in the tiled compressed writer, pair-owner selection, null-page ring convention) unverified. The pair-owner arithmetic itself checks out on paper (I replayed `write`/`mask`/`local` in numpy for context in {0,3,4,7,11}), but nothing exercises the kernels.
**Suggested comment:**
> `pooled_qsa_step` and everything it calls (`write_main_cache`, `write_compressed`, `read_ring_and_tags`, `write_ring_and_tags`) is not executed by any test in this PR - the lifecycle test runs `qsa_rpa.qsa_step`, and the only `pooled_qsa` test monkeypatches `streamindex_topk` away. Since this is the path #1968 actually uses and it is all aliased DMA code, could you add a pooled variant of `_check_lifecycle` here (reference oracle vs `pooled_qsa_step` on one FP8 and one BF16 pool), covering at least: a prefill whose `context % (2*ratio)` is in {4..7} (partial-pair merge), a decode that completes an odd group whose even partner was written in an earlier step, a request-slot reuse with context 0, and an inactive slot whose `ring_ids` entry is stale? CPU `interpret=True` is fine if TPU time is the constraint.

### F2. Prefill/decode routing is inferred from padded shapes, in both directions  [major]  `src/vllm_torchtpu/kernels/qwen4_exp/qsa_rpa.py:197`, `pooled_qsa.py:535`
`qsa_attention` picks the prefill kernels when `len(query) > len(starts) - 1` and `select_blocks` picks the ragged prefill schedule when `len(query) > len(context)`. anthonsu already raised the "multi-token prefill with `len(query) <= slots`" direction (still open). The reverse is at least as likely with vLLM's independent token/request padding: a pure decode step with e.g. 8 requests padded to a 16-token bucket has `len(query)=16 > 8` and is classified as prefill. It is still numerically correct (each request has q_len 1; `_effective_row_lengths` / the TC kernels handle that), but it goes to `adaptive_prefill` -> `_ragged_tc_write` (starts are not 256-aligned), which runs one 256-row TC tile per request for 8 tokens, and the StreamIndex prefill schedule runs a BQ128 block per request - the opposite of "decode keeps its existing path". Neither direction is covered by a test (`test_qwen_dispatch_preserves_existing_paths` uses `tokens=1` for decode and `tokens=256` with 1 or 2 slots for prefill).
**Suggested comment:**
> Both routing predicates (`len(query) > len(starts) - 1` here and `len(query) > len(context)` in `select_blocks`) assume the token bucket is <= the request-slot bucket for decode and > it for prefill. With the runner padding tokens and requests independently, a decode step of 8 requests in a 16-token bucket is routed to `adaptive_prefill` / `_ragged_tc_write` and to the BQ128 StreamIndex prefill schedule (correct output, but per-request 256-row TC tiles for 8 tokens). Could the runner pass an explicit static mode (e.g. `prefill: bool` derived from its bucket / `max_query_len > 1`) instead of inferring it from shapes, or at minimum document the invariant and assert it in #1968? This is the complement of the case anthonsu raised above.

### F3. Idle slots keep their stale `context` in the prefill schedule  [minor]  `src/vllm_torchtpu/kernels/qwen4_exp/pooled_qsa.py:545`
`seq_lens = context + query_lens` is passed for every slot below `num_seqs`, including idle slots with `query_lens == 0` whose `context` entry may be whatever the runner left there. In the unchunked schedule (`len(query) % 512 != 0`) `compute_batched_seq_metadata` gives such a sequence `s_num_bq = max(1, ...) = 1` block times `cdiv(kv_len, bkv_sz)` KV blocks, i.e. it scores a full KV sweep of a dead request into a zero-row output window. No wrong output (the window is 0 rows), just wasted steps and a dependency on the runner zeroing `context` for idle slots. The decode path already masks (`lengths = where(valid, logical + 1, 0)`), so this is an inconsistency.
**Suggested comment:**
> `seq_lens = context + query_lens` includes idle slots (`query_lens == 0`) with whatever `context` they carry; in the unchunked schedule those still get `max(1, ...)` query blocks x `cdiv(kv_len, bkv)` KV steps. Suggest `seq_lens = jnp.where(query_lens > 0, context + query_lens, 0)` so idle slots cost nothing and the kernel does not depend on the runner zeroing `context`, matching what the decode path does with `lengths`.

### F4. Ring/tag page 0 is a silent null page  [minor]  `src/vllm_torchtpu/kernels/qwen4_exp/qsa_state.py:120`, `pooled_qsa.py:669`
`write_ring_and_tags` only issues the DMA under `indices[...] > 0` (qsa_state.py:120/130) and reads clamp with `jnp.maximum(id, 0)` (qsa_state.py:44/50); `pooled_qsa_step` maps inactive slots to id 0 (pooled_qsa.py:669). So a request whose ring row was allocated block 0 would never have its raw-key ring / RoPE tags persisted and would read the shared null page next step - a silent numerics bug rather than an error. vLLM's `BlockPool` reserves block 0 as the null block, but this layer is "model-owned cache planning" and nothing here validates the assumption (no comment, no check).
**Suggested comment:**
> The ring/tag writer treats id 0 as "skip" and the reader treats it as the null page, so a request whose ring row is block 0 would silently lose its ring state. If the planner guarantees block 0 is the reserved null block, could you state that in the `write_ring_and_tags` / `pooled_qsa_step` docstrings (and ideally assert it at planning time in #1968)? If not, please use a separate validity mask instead of overloading id 0.

## Questions for the author
- Ring ownership when `context > 0` but the ring page was not written by this request: `_indexer_updates` (qsa.py:148, 176) trusts `ring[slot]` / `tags[slot]` whenever `context[req] > 0`. The reuse test only covers `context == 0`. What guarantees the page content for a prefix-cache hit at a non-group boundary (`context % ratio != 0`), a preempted request that is resumed with recomputation partially skipped, or a P/D transfer that moves KV/compressed pages but not the ring row? If those are excluded by the runner, where is that enforced?
- Compressed-key page span: both the writer (`write_compressed`, `pair = table[req, logical // pool.shape[1]] * pairs_per_page + ...`) and the reader (`select_blocks`, `logical_pages = pool.shape[1] // 128`) map one compressed page to `pool.shape[1]` tokens, i.e. 416 groups = 208 of the 1664 pair slots in an FP8 page (12.5 % utilisation; 1/16 for a BF16 KV2 pool). Is that span intentional (same page geometry as the main table so one allocator serves both), and is it what the #1968 planner sizes the compressed region for? If the compressed table is meant to be "independent" (module docstring), it would be safer to pass the span explicitly rather than reusing `pool.shape[1]`.
- `tuned_block_sizes.py:36/52`: the only BF16 entries are keyed on `(896, 1, 2, 256)` (one KV head, page 896), while every BF16 test/adaptive envelope in this PR uses `(1664, 2, 2, 256)` (KV2, page 1664). Is the 896 entry a TP=2 measurement? As written, BF16 Qwen pools at TP=1 silently fall to the serial DMA path with a `warning_once`.
- `select_blocks` / `select_decode_blocks` both compute weights as `jnp.full(q.shape[:2], d**-0.5)` and rely on the shared `reduce_heads` ReLU-then-weighted-sum. The reference (`select_groups`) is `relu(q.k).sum(heads) / sqrt(d)`. Fine for the current kernel, but worth a one-line comment that the per-head weight *is* the 1/sqrt(d) scale, since the unit `scales` from `BF16KeyReader` make it easy to double-apply later.
